Lab 2 · The pipeline that reruns

Raw files in, one tested table out, twice, same answer — 60 minutes

Aim

Build a pipeline that takes the raw files, applies the fixes you found today, passes its own quality contract, and produces one analysis-ready table. Then delete the output and run it again, and get the identical answer.

This is the Tuesday capstone checkpoint: your pipeline runs.

What “pipeline” means here

The word carries a lot of freight, so it is worth narrowing it before we start. We do not mean an orchestration platform, a scheduler, or anything you would need to procure. For today, a pipeline is simply this: a script that a person who is not you can run from a clean machine and get your number.

That is a modest-sounding standard and a demanding one. Most analytical work in most organisations does not meet it, not through any lack of care but because nobody ever asked it to — the work was done once, under time pressure, for a meeting that has since happened. Meeting the standard deliberately is what turns a piece of analysis into an asset somebody can inherit.

Five properties make the difference, and it is worth understanding what each is protecting against.

  1. It starts from the raw files, unmodified, in a folder nobody edits. If the inputs can change without anybody noticing, none of the other four properties can be relied on.
  2. Every step is in the script. No manual step, and in particular no “then I opened it in Excel and fixed the header.” A single manual step is enough to make the whole thing unrepeatable, and it is always the step nobody wrote down.
  3. It is idempotent. That word simply means running it twice produces the same result as running it once — nothing accumulates, nothing is appended to a file that was already there. Run it twice, get the same answer; run it on a clean machine, get the same answer.
  4. It tests before it publishes. The contract from 2.5 runs inside the pipeline, so bad data stops the run rather than reaching the output.
  5. It says what it did. Row counts at each step, printed as it goes. This is what lets you see a problem in the middle of the run rather than inferring it from a strange number at the end.

The shape

The diagram is worth reading as a sequence of five stages, because the ordering is the whole design. Raw files go in and are never edited. Cleaning happens next — types, deduplication, the entity fixes you found this afternoon — and produces a candidate table. That candidate then meets the gate, which is the quality contract, and only a table that passes goes on to be joined, derived and aggregated. Everything that emerges lands in outputs/, alongside the quality report that licensed it.

The gate sits where it does deliberately. Putting it after the modelling step would tell you that something was wrong only once you had a number in your hand and a temptation to keep it.

The reference implementation

Read this, then build your own. Do not copy it — the point of the lab is that you can explain every line, and an explanation is much harder to produce for code you have not typed.

Three versions follow, doing the same five stages in R, SQL and Python. Read whichever language you work in, then glance at one of the others: the structure is identical, which is the useful observation.

  • SQL
  • Python
# ---------------------------------------------------------------------------
# TDBG pipeline: raw sell-out files -> one analysis-ready weekly table.
# Run:  Rscript pipeline.R
# ---------------------------------------------------------------------------
library(tidyverse)
library(pointblank)

say <- function(step, tbl) message(sprintf("%-28s %8d rows", step, nrow(tbl)))

# --- 1. Read raw, types stated, nothing guessed ----------------------------
sales <- read_csv("data/fmcg_sell_out.csv",
                  col_types = cols(
                    week_starting  = col_date(),
                    depot_code     = col_character(),
                    sku            = col_character(),
                    units_sold     = col_double(),
                    unit_price_ngn = col_double(),
                    on_promotion   = col_integer(),
                    discount_pct   = col_double(),
                    stockout_flag  = col_integer(),
                    revenue_ngn    = col_double()))
say("raw sell-out", sales)

depots   <- read_csv("data/fmcg_depots.csv",   show_col_types = FALSE)
products <- read_csv("data/fmcg_products.csv", show_col_types = FALSE)

# --- 2. Clean -------------------------------------------------------------
# 2a. The ETL re-run left 214 duplicate grains. Grain is depot x sku x week.
sales <- sales |> distinct(week_starting, depot_code, sku, .keep_all = TRUE)
say("after dedupe", sales)

# 2b. Missing units on a stockout mean zero sold, not unknown. This is a
#     DECISION, recorded here so the next reader can disagree with it.
sales <- sales |>
  mutate(units_sold  = if_else(is.na(units_sold)  & stockout_flag == 1, 0, units_sold),
         revenue_ngn = if_else(is.na(revenue_ngn) & stockout_flag == 1, 0, revenue_ngn))

# 2c. The depot dimension has a rename inserted rather than applied. WHICH row
#     survives is a DECISION, and "the first one" would be an artefact of file
#     order. The rename is the newer, more specific name, so we keep the longer
#     one and record why. If your dimension has a valid-from date, use that
#     instead - it is the right answer and this file does not have one.
depots <- depots |>
  group_by(depot_code) |>
  slice_max(nchar(depot_name), n = 1, with_ties = FALSE) |>
  ungroup()
say("depot dimension", depots)

# --- 3. The gate ----------------------------------------------------------
agent <- create_agent(sales, tbl_name = "sell_out_clean",
                      label = "TDBG contract") |>
  rows_distinct(vars(week_starting, depot_code, sku)) |>
  col_vals_gte(units_sold, 0, na_pass = TRUE) |>   # na_pass: 2b decided what
                                                   # the remaining NAs mean
  col_vals_in_set(depot_code, set = depots$depot_code) |>
  col_vals_between(discount_pct, 0, 0.5) |>
  col_vals_expr(~ !(discount_pct > 0 & on_promotion == 0)) |>
  col_vals_not_null(revenue_ngn) |>
  interrogate()

export_report(agent, filename = "outputs/quality_report.html")

if (any(agent$validation_set$f_failed > 0, na.rm = TRUE)) {
  stop("Data contract failed. See outputs/quality_report.html")
}
message("contract passed")

# --- 4. Model -------------------------------------------------------------
weekly <- sales |>
  left_join(depots,   by = "depot_code", relationship = "many-to-one") |>
  left_join(products, by = "sku",        relationship = "many-to-one") |>
  mutate(gross_profit_ngn = revenue_ngn - units_sold * unit_cost_ngn,
         year = lubridate::year(week_starting))
say("after joins", weekly)   # MUST equal the row count after dedupe

stopifnot(nrow(weekly) == nrow(sales))   # the two-line habit, as an assertion

# --- 5. Publish -----------------------------------------------------------
dir.create("outputs", showWarnings = FALSE)
arrow::write_parquet(weekly, "outputs/fmcg_weekly.parquet")
write_csv(weekly, "outputs/fmcg_weekly.csv")
message("wrote outputs/fmcg_weekly.parquet  (", nrow(weekly), " rows)")

Three details in that script are worth pulling out, because they are the parts people tend to leave out when writing their own.

The say() helper at the top exists only to print a step name and a row count. It is four lines of no analytical value whatsoever, and it is what turns a silent script into one that narrates itself. When something goes wrong in three months, the run log tells you which stage it went wrong at.

Stating the column types explicitly in read_csv() rather than letting them be inferred looks like pedantry until the month a file arrives with an empty column, the guess changes, and everything downstream quietly behaves differently. Stated types make that a loud error on line one.

And the stopifnot() near the end is the two-line habit from 2.4 turned into something permanent. Counting rows by hand protects you on the day you remember to do it; an assertion in the script protects you on every future run, including the ones executed by somebody who has never heard of fan-out.

-- pipeline.sql   Run:  duckdb tdbg.duckdb < pipeline.sql

CREATE OR REPLACE TABLE depot_dim AS
SELECT depot_code, MAX(depot_name) AS depot_name,
       ANY_VALUE(region) AS region, ANY_VALUE(state) AS state
FROM read_csv_auto('data/fmcg_depots.csv')
GROUP BY depot_code;                              -- one row per depot, always

CREATE OR REPLACE TABLE sell_out_clean AS
SELECT DISTINCT ON (week_starting, depot_code, sku)   -- kills the 214
  week_starting, depot_code, sku,
  CASE WHEN units_sold  IS NULL AND stockout_flag = 1 THEN 0 ELSE units_sold  END AS units_sold,
  unit_price_ngn, on_promotion, discount_pct, stockout_flag,
  CASE WHEN revenue_ngn IS NULL AND stockout_flag = 1 THEN 0 ELSE revenue_ngn END AS revenue_ngn
FROM read_csv_auto('data/fmcg_sell_out.csv');

-- The gate. Any row returned here means stop.
SELECT 'grain not unique' AS breach, COUNT(*) - COUNT(DISTINCT (week_starting, depot_code, sku)) AS n
FROM sell_out_clean
UNION ALL SELECT 'orphan depot', COUNT(*) FROM sell_out_clean s
  LEFT JOIN depot_dim d USING (depot_code) WHERE d.depot_code IS NULL
UNION ALL SELECT 'negative units', COUNT(*) FROM sell_out_clean WHERE units_sold < 0;

CREATE OR REPLACE TABLE fmcg_weekly AS
SELECT s.*, d.depot_name, d.region, d.state,
       p.category, p.pack_size, p.unit_cost_ngn,
       s.revenue_ngn - s.units_sold * p.unit_cost_ngn AS gross_profit_ngn
FROM sell_out_clean s
JOIN depot_dim d USING (depot_code)
JOIN read_csv_auto('data/fmcg_products.csv') p USING (sku);

-- The assertion: the join must not have changed the row count.
SELECT (SELECT COUNT(*) FROM sell_out_clean) AS before_rows,
       (SELECT COUNT(*) FROM fmcg_weekly)    AS after_rows;

COPY fmcg_weekly TO 'outputs/fmcg_weekly.parquet' (FORMAT parquet);

The SQL version makes one thing more visible than the R version does: the depot dimension is rebuilt as a table that is unique by construction. Grouping by depot_code and taking one value of each attribute guarantees one row per depot, whatever arrives in the file next month. That is a different and stronger move than deleting the duplicate you happened to find today, and it is generally the right instinct — fix the shape rather than the instance.

# pipeline.py   Run:  python3 pipeline.py
import pandas as pd, pathlib, sys

def say(step, df): print(f"{step:<28}{len(df):>8,} rows")

raw = pathlib.Path("data")
out = pathlib.Path("outputs"); out.mkdir(exist_ok=True)

sales = pd.read_csv(raw / "fmcg_sell_out.csv", parse_dates=["week_starting"],
                    dtype={"depot_code": "string", "sku": "string"})
say("raw sell-out", sales)

sales = sales.drop_duplicates(subset=["week_starting", "depot_code", "sku"])
say("after dedupe", sales)

hard = sales.stockout_flag.eq(1)
sales.loc[hard, ["units_sold", "revenue_ngn"]] = \
    sales.loc[hard, ["units_sold", "revenue_ngn"]].fillna(0)

# One depot_code has two rows under two names. WHICH ROW SURVIVES IS A DECISION,
# and it belongs in the code where a reviewer can see it and disagree with it --
# not in whatever order the file happened to arrive in. Sorting the name
# descending keeps the longer, later name ("Abuja Central (Wuse II)") over the
# stub it replaced. Say so out loud when you present this, because the version
# of this line without the comment is indistinguishable from an accident.
depots = (pd.read_csv(raw / "fmcg_depots.csv")
            .sort_values(["depot_code", "depot_name"], ascending=[True, False])
            .drop_duplicates("depot_code"))

breaches = {
    "grain not unique": len(sales) - len(sales[["week_starting","depot_code","sku"]].drop_duplicates()),
    "negative units":   int((sales.units_sold < 0).sum()),
    "orphan depot":     int((~sales.depot_code.isin(depots.depot_code)).sum()),
}
if any(breaches.values()):
    sys.exit(f"Data contract failed: {breaches}")
print("contract passed")

weekly = (sales
          .merge(depots, on="depot_code", how="left", validate="many_to_one")
          .merge(pd.read_csv(raw / "fmcg_products.csv"), on="sku",
                 how="left", validate="many_to_one"))
assert len(weekly) == len(sales), "join changed the row count"
say("after joins", weekly)

weekly.to_parquet(out / "fmcg_weekly.parquet", index=False)
print(f"wrote outputs/fmcg_weekly.parquet ({len(weekly):,} rows)")

The breaches dictionary here is the whole quality contract compressed into three lines and a conditional. It is much less elegant than the pointblank report in the R version and it does the essential job just as well: if any count is above zero, the script exits with a message naming what failed. If you are building your first pipeline this evening and the reporting library feels like one thing too many, start here — a contract that is enforced plainly beats a beautiful report that never runs.

The comment that matters most

# 2b. Missing units on a stockout mean zero sold, not unknown. This is a
#     DECISION, recorded here so the next reader can disagree with it.

That comment is worth more than the line of code beneath it, and it is worth being precise about why.

Every pipeline contains judgement calls: what a missing value means, which of two duplicates to keep, where to draw a period boundary, which entity is the survivor of a merge. The code necessarily records what you decided, because it has to do something. Only the comment records that a decision was made at all — and that is the piece a successor needs, because you cannot revisit a choice you did not know was a choice.

Read the line without its comment and it looks like housekeeping: some nulls being tidied away. Read it with the comment and it is a documented position that a reasonable colleague might take differently, with the reasoning available to them. The code is the same either way; only one version can be argued with.

Write the comment as you go rather than afterwards. On Friday, when you come to write the model card, you will find it is mostly a matter of collecting them.

The two-run test

  • Delete the entire outputs/ folder.
  • Run the pipeline from the command line — not from inside your editor, from a terminal in a fresh session.
  • Record the final row count and one headline number.
  • Delete outputs/ again. Run again. Compare.
  • Now hand your script to the pair at the next table and have them run it on their machine.

That last step is where most pipelines fail on the first Tuesday: an absolute path, a package that was installed interactively, a file that only exists on your desktop. All three are worth finding today rather than in March.

Stretch

Put the pipeline under version control and commit it.

git init
git add pipeline.R data/ outputs/quality_report.html
git commit -m "Pipeline v1: dedupe, entity fix, contract, weekly table"

Then change one decision — treat missing units as missing rather than as zero — commit again, and look at the diff. That diff is a record of a judgement call, with a date and a name attached to it.

This is what “auditable” means in practice, and it costs about ninety seconds. When the regulator, the auditor or your successor asks why the number changed in March, the answer is a commit.

Copilot check

Ask the assistant to write this whole pipeline for you. It will, and it will be structurally good — sensible order, reasonable naming, decent error handling.

Then check the three things it cannot know:

  1. Which duplicate survives. It will keep the first row. Is that right? In the depot dimension the newer name is the correct survivor, and “first” is an artefact of file order.
  2. What missing means. It will either drop nulls or fill them with zero, and it will not flag that it chose.
  3. Whether the assertion should be fatal. It writes warnings where you need failures, because it does not know what the number is for.

Three decisions, none of them technical, all of them yours. This is the whole week in one lab.
