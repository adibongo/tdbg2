SQL as the lingua franca

Six verbs, read rather than written — Session 2.1, 60 minutes

Aim

By the end of this session you can read any SQL query an assistant hands you, say out loud what it does to the data, and name the one place where it could be silently wrong. You will not be writing SQL from a blank page. Nobody does that any more, and it was never the valuable part.

Why SQL, and why writing it is no longer the point

SQL is the one language that every data platform you will ever buy has in common. Your warehouse speaks it. Power BI generates it underneath the visuals. Your core banking extract is defined in it. Your data team argues about business rules in it. It has outlived four generations of tooling around it and it will comfortably outlive the current one — so the ability to read it is a durable skill in a field where most skills are not.

What has changed is that it has become readable in an afternoon. The expensive part of learning SQL was never the vocabulary; it was the blank page — knowing which of six constructions to reach for and in what order, which took months of practice. That part is now handled for you, on request, in seconds.

So this session inverts the usual teaching order. You will not learn to compose queries. You will learn to read, predict and audit them. The test at the end is not “can you write this?” but “can you say what this query will do to the data before you run it, and be right?” That skill is what lets you supervise work you did not do — which, for most people in this room, is the actual job.

The six verbs

Every analytical SQL query in existence is some arrangement of six ideas. Learn the ideas and the syntax stops being the obstacle.

Verb The idea SQL The one-word version
1 Pick rows WHERE filter
2 Pick columns SELECT choose
3 Make new columns SELECT ... AS derive
4 Collapse to groups GROUP BY summarise
5 Put in order ORDER BY arrange
6 Bring tables together JOIN combine

Five of those six are safe, in a specific sense: if you get them wrong, you generally get an obviously wrong answer or an error. The sixth behaves differently. A join can quietly change how many rows you have, and every total computed afterwards changes with it — with no error, no warning and a result that still looks entirely plausible. That is why it has a session to itself this afternoon.

The same six ideas exist in R’s tidyverse and in Python’s pandas, with different spellings. Learn them once as ideas and you can read all three, which matters because your organisation almost certainly contains all three.

  • SQL
  • R (tidyverse)
  • Python (pandas)
SELECT
  depot_code,                                    -- choose
  SUM(units_sold)  AS units,                     -- summarise
  SUM(revenue_ngn) AS revenue,                   -- summarise
  SUM(revenue_ngn) / SUM(units_sold) AS asp      -- derive
FROM 'fmcg_sell_out.csv'
WHERE week_starting >= DATE '2025-01-01'         -- filter
  AND on_promotion = 0
GROUP BY depot_code                              -- summarise, by what
ORDER BY revenue DESC;                           -- arrange
library(tidyverse)

read_csv("data/fmcg_sell_out.csv") |>
  filter(week_starting >= as.Date("2025-01-01"),   # filter
         on_promotion == 0) |>
  group_by(depot_code) |>                          # summarise, by what
  summarise(units   = sum(units_sold,  na.rm = TRUE),
            revenue = sum(revenue_ngn, na.rm = TRUE)) |>
  mutate(asp = revenue / units) |>                 # derive
  arrange(desc(revenue))                           # arrange
import pandas as pd

df = pd.read_csv("data/fmcg_sell_out.csv", parse_dates=["week_starting"])

(df[(df.week_starting >= "2025-01-01") & (df.on_promotion == 0)]
   .groupby("depot_code")
   .agg(units=("units_sold", "sum"), revenue=("revenue_ngn", "sum"))
   .assign(asp=lambda d: d.revenue / d.units)
   .sort_values("revenue", ascending=False))

Read the three side by side and follow one verb through all of them — the filter, say. Same idea, three spellings, and none of the differences is conceptual. Once that is visible, the “which language should we standardise on?” debate becomes a good deal less consequential than it usually feels to the people having it. What matters is that everybody can read the answer, and the ideas above are the part that transfers.

The na.rm = TRUE in the R version is a decision, not a default

That argument tells R to ignore missing values when it adds the column up. It is typed so routinely that it hardly registers as a choice — but it is one.

In this dataset, 789 rows have a missing units_sold, because a stockout was recorded as “unknown” rather than as zero. Dropping those rows removes the worst trading weeks from any average you compute, which pushes the answer upward in a way nothing on screen will indicate. SQL’s SUM does exactly the same thing, and without even a flag to remind you it happened.

Neither behaviour is wrong, and neither is a bug. Both simply require a decision from you: is missing here the same as zero? In this dataset the two are close — the depot sold nothing because it had nothing to sell — so treating the blanks as zeroes is defensible, and worth writing down. In a survey dataset the two are emphatically different, and treating a non-response as a zero would be a serious error. The code cannot tell the difference between those cases, and neither can the assistant that wrote it. You can, because you know where the data came from.

Reading a query out loud

Here is the discipline, and it is worth practising deliberately for a week until it becomes automatic: before you run anything, say what it does in English, in the order the database will actually do it.

Take this one:

SELECT p.category,
       COUNT(DISTINCT s.sku)              AS skus,
       SUM(s.revenue_ngn)                 AS revenue,
       AVG(s.discount_pct)                AS avg_discount
FROM 'fmcg_sell_out.csv' s
JOIN 'fmcg_products.csv' p USING (sku)
WHERE s.on_promotion = 1
GROUP BY p.category
HAVING SUM(s.revenue_ngn) > 1e9
ORDER BY revenue DESC;

Out loud, in execution order:

Take the sell-out rows. Attach product attributes by SKU. Keep only the promotional weeks. Collapse to one row per category. Count distinct SKUs, total the revenue, average the discount. Then throw away any category whose total is under a billion naira. Sort by revenue.

Notice that the reading order is not the writing order: the database starts with the tables and the filters, does the grouping next, and only then applies HAVING and the sort. Once you read queries in that order, two things in this one stand out — and neither is a question of syntax.

AVG(s.discount_pct) is an unweighted average of week-rows. Every row counts equally, regardless of how much money went through it. Take a category with two SKUs on promotion in a week: one sells ₦100m at a 5% discount, the other sells ₦2m at a 40% discount. AVG reports 22.5%, because it averages 5 and 40. The discount you actually paid is (100 × 5 + 2 × 40) ÷ 102, which is about 5.7% — the small SKU had a deep discount and almost none of the volume. If the question is “what discount are we actually paying?”, the answer is SUM(units*price*discount)/SUM(units*price) rather than AVG. This is among the most common quiet errors in commercial SQL, and it is invisible in the output, because a wrong average looks exactly like a right one.

HAVING filters after grouping; WHERE filters before. In this query, WHERE decides which rows go into each category total and HAVING decides which category totals survive. Move the condition from one to the other and you are asking a different question — the first would drop individual weeks below a billion naira, which is not what anybody meant. Assistants generally place these correctly. Humans reading assistants’ output frequently do not notice which one was used, and the two produce results that are equally plausible on the page.

The read-aloud test

If a query cannot be said in English in under twenty seconds, it is doing too much at once to be reviewed reliably.

The fix is to break it into named steps using a CTE — WITH step_one AS (...), step_two AS (...) — where each step is named for what it produces. A CTE, or common table expression, is simply a temporary named result you can build the next step on top of. The database does not care either way; the person reviewing the query in six months does, and so do you in six months.

You can ask for this directly: “rewrite this as a sequence of named CTEs, one per logical step, with a comment on each saying what it produces and what its grain is.” What comes back is something you can audit a step at a time, which is a different kind of artefact from something you can only run and hope.

Window functions — the one advanced thing worth knowing

There is exactly one piece of so-called advanced SQL that repays the effort immediately in commercial work: the ability to calculate something per group without collapsing the rows away.

The ordinary GROUP BY gives you one row per depot and loses the detail underneath. Often that is not what you want — you want to keep every SKU line and, beside it, that SKU’s share of its depot’s total. That is what a window function does.

-- Each SKU's share of its depot's revenue, and its rank within the depot.
SELECT
  depot_code,
  sku,
  SUM(revenue_ngn) AS revenue,
  SUM(revenue_ngn) / SUM(SUM(revenue_ngn)) OVER (PARTITION BY depot_code) AS share,
  RANK() OVER (PARTITION BY depot_code ORDER BY SUM(revenue_ngn) DESC)    AS rank_in_depot
FROM 'fmcg_sell_out.csv'
GROUP BY depot_code, sku
QUALIFY rank_in_depot <= 5
ORDER BY depot_code, rank_in_depot;

The phrase to hold on to is OVER (PARTITION BY ...), which says: do this calculation separately within each depot, but keep all the rows. The word “partition” here means nothing more sinister than “group, for the purposes of this one calculation”. That single construction is how you get shares, ranks, running totals, moving averages, period-on-period changes and “compared with the same week last year” — which between them account for most of what a commercial dashboard actually contains.

You will not be asked to write this from memory. You will be asked to read it and say what it produces, which, having read the paragraph above, you can now do.

Core lab · 30 minutes

Driver and Sceptic. Swap roles from yesterday.

  • Ask the assistant: “top 5 SKUs by revenue in each depot for 2025, from fmcg_sell_out.csv, DuckDB SQL.” Do not run it yet.
  • Sceptic reads it aloud in English before it runs. Predict the number of rows.
  • Run it. Were you right? If not, why not?
  • Now ask for “average discount by category”. Read it. Is it weighted? Fix it.
  • Ask the assistant to rewrite your fixed query as named CTEs with grain comments.
  • Add today’s failure logbook entry.

Predicting the row count before running is the part that feels artificial and is the part that teaches. A prediction you got wrong is a precise piece of information about which part of the query you misread.

Stretch

Commission — and then audit — a query that answers this: which SKU–depot combinations have both above-median revenue and above-median stockout rate? Those are the lines where poor availability is costing real money rather than notional money, and it is precisely the shortlist a supply planner could act on next week.

Then the harder version: express it as a single query using window functions rather than two queries and a join. Ask the assistant for it, then explain to your Sceptic why the result is correct. If you cannot explain it, you have a query you can run but not defend, which is the thing this session exists to prevent.

Copilot check

Three failure modes turn up in assistant-written SQL often enough to be worth watching for, in rough order of frequency:

  1. Column names that do not exist. Where you have not supplied a schema, one gets inferred, and the inference is plausible rather than correct. Pasting the column list takes ten seconds and removes most of the problem.
  2. AVG where you needed a weighted average. The request is answered literally, and “average discount” literally means the average of the discount column.
  3. Dialect drift. QUALIFY works in DuckDB and Snowflake but not in PostgreSQL, and EXTRACT syntax varies between engines. Naming the dialect in the prompt — “DuckDB SQL” — settles it.

And one more that is not a failure of the machine at all: it will happily aggregate a table that has never been deduplicated, because it has no way of knowing whether the rows in front of it are the rows that should be there. You will have a way of knowing from about 2pm today.

Takeaways

  1. Six ideas: filter, choose, derive, summarise, arrange, combine. Five are safe.
  2. Read queries aloud in execution order before running them.
  3. AVG is rarely the average you meant in a commercial context.
  4. Ask for named CTEs with grain comments. It is the difference between code you can audit and code you can only trust.
