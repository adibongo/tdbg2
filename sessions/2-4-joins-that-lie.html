Joins that lie

Grain, keys, fan-out, and the Abuja revenue that doubled itself — Session 2.4, 60 minutes

Aim

By the end of this session you will have personally produced a completely wrong number that looked entirely correct, understood exactly why it happened, and installed a two-line habit that prevents the whole family of errors for the rest of your career. Producing the wrong number yourself is the point: it is a great deal more memorable than being told about it.

Why we give this hour to something so unglamorous

Sessions on modelling and on AI get the attention, and both matter. But if you audited a year of expensive analytical mistakes across a portfolio of real companies — the ones where a decision was taken on a number that was not true — very few would turn out to be statistical. The great majority are about joins, grains, definitions and calendars: four mechanical things that determine whether the rows going into a total are the rows that ought to be there.

These errors are hard to catch for a sympathetic reason. They do not produce anything that looks wrong. The output is well formatted, the magnitude is plausible, the ranking is sensible, and the totals foot. A reviewer reads a table like that the way any sensible person does — by checking whether the conclusion makes sense — and the conclusion does make sense, because it was computed correctly from the wrong number of rows.

It is worth saying plainly what an assistant can do for you here, because this is one of the few places in the week where the honest answer is “not much”. Ask it to write the join and it will write a correct join. The problem lives in the data rather than in the code, and the assistant has never seen your data. That gap — between code that is right and data that is not what the code assumes — is where the rest of this hour lives.

Do this now, before reading on

The demonstration works far better if you run it yourself first, so resist the temptation to read ahead. Two queries. The first counts the rows in the fact table — the big transactional file of weekly sell-out. The second attaches the depot dimension, which is the small reference table holding each depot’s name, region and state, and totals revenue by region.

-- 1. How many rows in the fact table?
SELECT COUNT(*) FROM 'data/fmcg_sell_out.csv';

-- 2. Attach the depot dimension and total the revenue by region.
SELECT d.region,
       ROUND(SUM(s.revenue_ngn) / 1e9, 2) AS revenue_bn
FROM 'data/fmcg_sell_out.csv' s
JOIN 'data/fmcg_depots.csv'   d USING (depot_code)
GROUP BY d.region
ORDER BY revenue_bn DESC;

Write down the region ranking somewhere you can find it again. Note in particular which region comes second — we will come back to that.

Now run the same join a third time, and this time do not summarise anything. Simply count how many rows the join produced.

SELECT COUNT(*)
FROM 'data/fmcg_sell_out.csv' s
JOIN 'data/fmcg_depots.csv'   d USING (depot_code);
What just happened

55,474 rows went in. 60,094 came out.

That is 4,620 rows that did not exist a moment ago, and no error message anywhere. The transferable part is the principle rather than the cause: a join to a dimension table should never increase the row count. A dimension exists to describe things — one row per depot, one row per product, one row per customer — so attaching it should add columns to the rows you already had, never rows.

The cause here is that fmcg_depots.csv contains thirteen rows for twelve depots. Somebody renamed Abuja Central to “Abuja Central (Wuse II)” and inserted the new name as a fresh row rather than updating the existing one — an entirely ordinary thing to do, since the old row has history attached and deleting it feels risky. But the key DP04 now appears twice, so every Abuja Central sell-out line found two matching dimension rows, and the join dutifully emitted one output row for each.

Here is what a board would see, in the order they would see it:

Rows Abuja Central revenue Region ranking
As shipped 55,474 ₦4.51bn North Central 4th
After the join 60,094 ₦9.03bn North Central 2nd

The revenue figure is the tell. Each Abuja Central row is counted exactly twice, so its revenue exactly doubles: ₦4.51bn becomes ₦9.03bn, the last digit differing only because each total is rounded independently. A figure that is precisely double a plausible one should send you looking for duplication first.

(“As shipped” is not the same as “correct”. The file still carries 214 duplicate grains from the ETL re-run, which is a second overstatement sitting underneath this one. Two separate defects, two separate corrections, and you have to do both — which is itself a useful lesson, because finding one problem creates a strong and misleading feeling that you have finished.)

Follow it through to the network total. That duplicated ₦4.51bn is a straight addition to a total that was previously right, and it lifts network revenue by 9.6%. Abuja Central overtakes both Lagos depots to become the largest single site in the network. If a colleague were assembling an expansion case for the North that month, this is the table they would have reached for, and it would have supported the case handsomely.

Notice what would not have saved you. Nothing about the query is wrong. Run it past a reviewer, a linter or an assistant and it passes all three. The only thing that catches it is counting the rows.

Why it happens: fan-out

A join multiplies rows. That is not a defect; it is the entire mechanism. For every row on the left, the database looks for matching rows on the right and emits one output row per match. If there is exactly one match, the row count is preserved. If there are two, the row is emitted twice. The behaviour is the same in either case, and so is the absence of any warning.

The technical name for the second case is fan-out: one input row fanning out into several output rows. It is worth knowing the word, because it is what a data engineer will say when you ask them what went wrong, and because it names a family rather than an incident.

Left grain Right grain Result
One row per order line One row per product Safe — many-to-one
One row per order line Two rows per product Every line doubles — fan-out
One row per customer Many rows per customer (addresses) Customer count inflates
One row per day One row per day per region Days multiply by regions

Read that as a sequence rather than a list. The first row is the arrangement you intended: many facts, one description of each thing they refer to. The other three are what happens when the right-hand side turns out to hold more than one row per thing, whether you knew it or not. In practice the cause is almost always one of four:

  1. A duplicate in the dimension — a rename, a merge of two systems, a re-load that appended instead of replacing. That is what has happened in today’s file.
  2. A key that is not unique in the way you assumed. A customer_id that turns out to be unique per branch rather than per customer is the classic. Nothing in the column name tells you which it is.
  3. A slowly-changing dimension without a date filter. Some dimensions deliberately keep history — one row per version of a customer’s address, each with valid-from and valid-to dates. Joined without a date condition, every version attaches to every transaction. The design is correct; the join was incomplete.
  4. A join on something that was never a key. Joining on a name, or on a code that got retired and then reused five years later.

None of these is a sign of carelessness. Three of the four are the ordinary consequences of systems that have run for a long time and accumulated history, which is what useful systems do.

The two-line habit

Here is the habit, and it is the highest-return four seconds in this programme: count the rows before the join, and count them again afterwards. If the number moved and you did not expect it to, stop and find out why before you look at any total. The third check — the one that would have caught today’s problem in advance — asks whether the key on the right-hand side is actually unique.

  • SQL
  • R
  • Python
-- Before
SELECT COUNT(*) AS before_rows FROM 'data/fmcg_sell_out.csv';

-- The check that should have been done first: is the key unique?
SELECT depot_code, COUNT(*) AS n
FROM 'data/fmcg_depots.csv'
GROUP BY depot_code
HAVING COUNT(*) > 1;
-- DP04 | 2      <- there it is

-- After
SELECT COUNT(*) AS after_rows
FROM 'data/fmcg_sell_out.csv' s
JOIN 'data/fmcg_depots.csv'   d USING (depot_code);

The middle query is the pattern worth memorising: group by the column that is supposed to be unique, count the rows in each group, keep only the groups with more than one. A genuinely unique key returns nothing at all. Anything that comes back is a fan-out waiting to happen.

library(tidyverse)

sales  <- read_csv("data/fmcg_sell_out.csv")
depots <- read_csv("data/fmcg_depots.csv")

# Is the key unique on the right-hand side?
depots |> count(depot_code) |> filter(n > 1)

# dplyr will warn you about this one if you let it
joined <- sales |>
  left_join(depots, by = "depot_code", relationship = "many-to-one")
# Error: Each row in `x` must match at most 1 row in `y`.

nrow(sales); nrow(joined)

relationship = "many-to-one" is a small argument with a large effect. It states your assumption — many fact rows, at most one dimension row each — and asks the software to enforce it, so a false assumption produces an error rather than a wrong answer. One phrase per join, and it is the most valuable argument in the tidyverse.

import pandas as pd

sales  = pd.read_csv("data/fmcg_sell_out.csv")
depots = pd.read_csv("data/fmcg_depots.csv")

# validate= raises instead of silently fanning out
joined = sales.merge(depots, on="depot_code", how="left", validate="many_to_one")
# MergeError: Merge keys are not unique in right dataset

print(len(sales), len(joined))

validate="many_to_one" does in pandas exactly what relationship= does in dplyr: it turns a silent duplication into a loud failure at the moment it happens, rather than a puzzling number three steps later.

The two questions, for people who will never write a join

You do not need to know what a join is, or to write a line of code, to prevent this happening in work you commission. You need two questions, and you can ask them of anybody presenting you a number:

  1. “One row per what?” — asked of each table that went into the analysis.
  2. “How many rows before the join, and how many after?”

If the answer to the second is “I don’t know”, the number is not ready yet, and saying so is not a criticism of the analyst — it is a request for one more query that takes four seconds. If the row count did change and nobody had predicted that it would, that is the moment to pause rather than to press on.

Ask these once in a meeting, pleasantly, and you will notice the quality of what you are shown afterwards change. Not because anybody was being careless, but because a check that somebody senior is known to ask about is a check that gets run.

The second one: when one entity arrives as two

The first defect inflated a number. This one does the opposite: it hides something valuable by splitting it in half. Run the supplier scorecard.

SELECT supplier_id,
       COUNT(*)                                   AS orders,
       ROUND(AVG(on_time), 3)                     AS on_time_rate,
       ROUND(SUM(order_value_ngn) / 1e9, 2)       AS spend_bn
FROM 'data/supply_chain_pos.csv'
GROUP BY supplier_id
ORDER BY spend_bn DESC;

Nine rows come back. A category manager reading that table sees a fairly even spread of spend with nobody standing out, concludes there is no obvious consolidation opportunity, and moves on. That is a reasonable reading of the table in front of them.

Before opening the panel below, try the question the table cannot answer on its own: how many suppliers does this business actually have?

What nine IDs are really describing

SUP-CEDAR was renamed SUP-CEDAR-NG in March 2025, and both identifiers remain live in the file. The scorecard therefore shows one supplier as two mid-sized ones, at 6.6% and 7.4% of spend respectively.

Add those together and Cedar is 14.0% of spend — the third largest relationship this business has, behind Alpha at 18.6% and Bridge at 16.2%. That alone would change the shortlist for a consolidation conversation. The service figure changes the conversation altogether: Cedar delivers on time on 98.5% of orders, against a network average of 77.4%, and the next best supplier in the file manages 85.9%.

So Cedar is not merely good. It is, by a wide margin, the best supplier this business has, and it is being under-used. The scorecard conceals that not through any error of arithmetic but by presenting it as two unremarkable halves, neither large enough to draw the eye. The consolidation opportunity — worth several points of network service level — never reaches the meeting, and nobody involved does anything wrong.

The fix strips the -NG suffix, then groups by the cleaned identifier.

-- The fix, and the reason entity resolution is a commercial issue
SELECT regexp_replace(supplier_id, '-NG$', '') AS supplier,
       COUNT(*)                                AS orders,
       ROUND(AVG(on_time), 3)                  AS on_time_rate,
       ROUND(SUM(order_value_ngn) / 1e9, 2)    AS spend_bn
FROM 'data/supply_chain_pos.csv'
GROUP BY 1
ORDER BY spend_bn DESC;

Deciding that two identifiers refer to the same real-world thing is called entity resolution. It sounds like a technical speciality, and it is usually a commercial judgement: are these two account numbers one customer or two? Is this subsidiary the same counterparty as its parent, for the purposes of an exposure limit?

The question that finds it: how many distinct real-world things is this key supposed to represent? Somebody has to hold the count in their head — eight suppliers — and compare it with what the file says. That reconciliation is not something the assistant can do for you, because only one of you has ever met the suppliers.

Grain, stated once and for all

Both defects above are the same idea seen from two sides, so it is worth stating that idea carefully and giving it its proper name.

The grain of a table is what one row represents.

If you cannot say the grain in a single sentence — “one row per depot, per SKU, per week”, “one row per purchase order”, “one row per customer as at today” — then you cannot safely trust any total computed from it, because you do not know what you are adding up. Writing the grain at the top of a script takes ten seconds and is the most useful comment in most pipelines.

Two grain errors cost real money regularly and are rarely taught anywhere.

Mixed grain inside one table. A sales extract containing both line items and order-level freight rows. Both carry a value, both are called “revenue” in the source system, and summing the value column double-counts the freight. Extremely common in ERP extracts, and nobody’s mistake: the source system represents two legitimate things and the extract has flattened them into one shape.

Silent grain change over time. A table that held one row per day until March and one row per day per channel afterwards, because a field was added and the extract widened to match. Every year-on-year comparison spanning March is now wrong, and nothing in the file announces it. The cheapest way to detect it is to count rows per period and look at the sequence: a genuine business trend drifts, whereas a grain change steps.

-- The grain-change detector. Run it on any time series you inherit.
SELECT week_starting, COUNT(*) AS rows_this_week
FROM 'data/fmcg_sell_out.csv'
GROUP BY 1
ORDER BY 1;
-- Look for step changes, not gradual drift.

Run that on any time series somebody hands you. It takes seconds, it needs no knowledge of the business, and a flat line with one sudden step in it tells you more about the file than an hour of reading its documentation would.

Core lab · 35 minutes

  • Reproduce the Abuja result. Present it to your table as a finding, with a straight face, before revealing it.
  • Find the duplicate. Quantify the damage in naira and in ranking.
  • Fix it two ways: deduplicate the dimension, and add the relationship / validate guard so it can never happen silently again.
  • Now the supplier scorecard. Nine IDs, eight suppliers. Find it and quantify the missed opportunity.
  • Run the grain-change detector on all four FMCG files.
  • Two entries in the failure logbook today. This session earns them.

The presentation step in the first item is not a joke. Watching a room accept a wrong number politely, including the people who would normally ask good questions, is the most efficient way to understand why these errors survive review in your own organisation.

Stretch · break another table’s result

Take a finished query from a table that has moved on, and find a way to make its answer wrong without touching the query at all — only the data underneath it. Add a duplicate row to a dimension. Introduce a renamed entity. Change one table’s grain halfway through the period.

Then hand it back, without comment, and see whether they catch it.

This is the most useful stretch exercise in the programme, and it is worth saying why. Every other exercise builds a procedure: run this check, ask this question. This one builds an adversarial instinct — the habit of asking how a correct-looking result could have come from incorrect data — and that is the part an assistant cannot supply, because it requires imagining a world other than the one described in the prompt.

Copilot check

Try this pair of prompts in sequence, because the contrast between the two answers is the lesson.

First ask: “Here is my join. What could make it produce more rows than it should?”

You will get an excellent, complete, textbook answer — duplicate keys, one-to-many relationships, missing date filters on slowly-changing dimensions, keys that are unique at a different level than assumed. Every item correct, and a genuinely useful checklist.

Then ask: “Does that happen with my data?”

It cannot know. A well-behaved assistant will say so; a less careful one will produce a confident-sounding guess that reads exactly like the first answer did. The distance between those two responses is roughly the job description of everybody in this room: the checklist is available to anyone, and the knowledge of which item on it applies today is not.

Takeaways

  1. Most expensive analytical errors are joins, grains, definitions and calendars — not statistics.
  2. Count rows before and after every join. Four seconds.
  3. Use relationship = "many-to-one" in R or validate= in pandas so silent fan-out becomes a loud error.
  4. Ask how many real-world things a key is supposed to represent, then check.
  5. “One row per what?” is the question. Ask it of every table, including the ones you are handed in a meeting.
