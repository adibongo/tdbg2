One source, five outputs

A document that regenerates itself — Session 4.3, 60 minutes

Aim

By the end of this session you can write one document that produces a PDF, a Word file, a web page, a slide deck and a dashboard from a single source, with every number in it computed rather than typed — so that when the data updates, the document updates, and nothing disagrees with anything else.

If your Tuesday pipeline did not finish

Everything below reads outputs/fmcg_weekly.parquet — the deduplicated, null-resolved, dimension-joined table that Tuesday’s lab produces.

A reference build of that exact file ships with the course data, in outputs/. If your own pipeline is not finished, point today’s code at the reference build and carry on. You will fix your pipeline at the next break or this evening; you will not spend this morning catching up while the room moves on without you.

Nobody is marked down for this. The capstone checkpoint asks whether your pipeline runs by Friday, not whether it ran by Wednesday at nine.

The problem, which everybody has

Picture the last few days of a month end. An analyst produces the numbers. Somebody types a selection of them into a deck for the executive committee. Somebody else types a smaller selection into a Word memo for the audit committee. A third person, working from the same underlying extract but a slightly earlier version of it, builds the dashboard. Then the CFO asks a good question late on the Thursday, one number is recomputed, and the corrected value is patched into the deck — because the deck is the thing being presented on Friday — and not into the other two.

There are now four documents in circulation and at least two of them are wrong. Nobody was careless. The transcription happened under time pressure, it happened in three different places, and there was never a moment at which anyone could have seen all four versions side by side. This is a structural property of copying numbers between documents rather than a property of the people doing the copying, which is why it recurs in organisations that are otherwise extremely well run.

The second half of the problem arrives later. In March somebody asks why the December figure was restated, and the honest answer is that nobody can reconstruct it, because the calculation lived in a spreadsheet cell that has since been overwritten by the January calculation. The number was right, or it was wrong, and there is now no way to establish which.

The fix has been well understood for thirty years and it is simpler than it sounds: the document contains the code that produces its own numbers. Prose and calculation live in the same file. Nothing is transcribed. When the data changes you re-render, and every number, chart and table in the document updates together — or the render fails loudly and tells you which line it could not compute, which is also a perfectly good outcome, because a document that refuses to build is one you cannot circulate by accident.

The technical name for this is literate programming, and the tool we will use for it is Quarto. You will meet the idea again under other names — R Markdown, Jupyter Book, notebooks — but the underlying move is always the same one: put the sentence and the sum in the same place, so they cannot drift apart.

What this actually buys you

Consistency. The number in the memo, the deck and the dashboard cannot disagree, because there is only one of it. Every appearance is the same computation rendered in a different place.

Speed at month end. The first month is slower, and it is worth saying that plainly rather than discovering it: you are building the machine as well as the report. Every month after that is a single command. Teams that adopt this typically take a 10-day close narrative down to under a day of analyst time, and the saving compounds because the reclaimed days go into analysis rather than into assembly.

Auditability. “Why did the December figure change?” acquires an answer: a commit, with a date, a name and a diff showing exactly which line of code moved and what it moved to.

Version control that means something. You can diff a document — see, line by line, what changed between one version and the next. You cannot meaningfully diff a spreadsheet, and you certainly cannot diff a slide.

The shape of the source

Everything lives in one file: the prose you want people to read, and the code that produces the numbers inside it. Read the example below for its shape rather than its syntax — the block at the top is configuration, the block in the middle is the calculation, and the part at the bottom is the report itself.

---
title: "Depot availability, Q1 2026"
author: "Supply Analytics"
date: today
format:
  html:  {toc: true}
  pdf:   {documentclass: scrreprt, geometry: [margin=1in]}
  docx:  {reference-doc: templates/lbs-report.docx}
  revealjs: {theme: [default, templates/lbs.scss]}
execute:
  echo: false
  warning: false
---

```{r setup}
library(tidyverse)
weekly <- arrow::read_parquet("outputs/fmcg_weekly.parquet")

# Q1 2026 is the last complete quarter in the shipped file, which stops on
# 2026-03-30. Q2 is deliberately held back for Wednesday's forecast market, so
# no participant-facing code may reference it -- filter on it and every number
# below renders as NaN, in the one session about documents that stay true.
q1 <- "2026-01-01"
availability <- 1 - mean(weekly$stockout_flag[weekly$week_starting >= q1])
worst <- weekly |>
  filter(week_starting >= q1) |>
  summarise(rate = mean(stockout_flag), .by = depot_name) |>
  slice_max(rate, n = 1)
```

## Summary

Network availability in Q1 was **`r scales::percent(availability, 0.1)`**, against a
target of 97.0%. The weakest depot was **`r worst$depot_name`** at
**`r scales::percent(1 - worst$rate, 0.1)`**.

```{r}
#| label: fig-availability
#| fig-cap: "Weekly availability by depot, Q1 2026. The target line is 97%."
# ... chart code ...
```

Two things in that example are doing the real work, and both are worth slowing down for.

Inline code. The construction `r scales::percent(availability, 0.1)` sits inside an ordinary English sentence and is replaced, at render time, by a computed number. Nobody typed 96.9% into that paragraph. The document works out the availability figure from the weekly table, formats it as a percentage to one decimal place, and drops the result into the sentence. Change the data and the sentence changes with it. Notice too that the same technique picks the name of the weakest depot: `r worst$depot_name`. Text can be computed as readily as arithmetic, which means an exception list, a ranking or a “the three depots below target were…” sentence can all maintain themselves.

One YAML block, five formats. The section between the two --- lines at the very top is the front matter — configuration for the whole document, written in a format called YAML. The format: key lists everything this one source can become. A single command, quarto render report.qmd, produces all of them, and none of them is a copy of any of the others; each is a fresh rendering of the same source.

The single highest-value habit in this session

Never type a number into prose.

Not once. Not “just this one, it will not change”. Every number in every sentence is inline code that computes it.

This is the discipline that makes the whole arrangement hold, and it is the first one to go under time pressure — usually at eleven o’clock at night, on the one figure that is genuinely awkward to compute, with an entirely reasonable intention to come back and fix it properly. It happens to careful people, and it happens for good reasons.

It is worth resisting anyway, because of what it costs later. The moment one number is typed, the document can disagree with itself, and it eventually will — most often three months later, in front of somebody senior, when the typed figure is the only one on the page that did not move. A useful safeguard: if a number is hard to compute inline, compute it in the setup block and give it a name. value_mid in a sentence is still code, and it is far easier to read than a nested expression.

Five outputs, one command

quarto render report.qmd                 # every format in the YAML
quarto render report.qmd --to pdf        # just the board PDF
quarto render report.qmd --to docx       # for the person who needs to track changes
quarto render report.qmd --to revealjs   # the deck
quarto render dashboard.qmd              # the screen

Each of those outputs has a different reader with a different habit, and the last column of the table below is the thing that most often gets overlooked when a team first tries this.

Output Who it is for The one thing to get right
HTML The team, day to day Self-contained, so it survives being emailed
PDF The board pack Page breaks, page numbers, a real title page
Word Legal, compliance, anyone who tracks changes Use a reference doc so it lands in house style
reveal.js Presenting it One idea per slide; the appendix carries the detail
Dashboard The recurring decision Session 4.2

On Word specifically, because it is where this proposal usually meets its first objection. Organisations that insist on Word are generally right to insist on it: their review process depends on tracked changes, comments and a named person signing off a specific version, and none of that works in a PDF. The reference-doc: setting exists for exactly this. You supply an ordinary Word document carrying your house styles — the heading fonts, the table borders, the margins your communications team has already decided on — and Quarto writes its content into that skeleton, so the generated file arrives already looking like everything else the organisation produces. It is a two-line change, it removes the most common corporate objection to reproducible reporting outright, and almost nobody knows it exists.

Parameters — the same report, twelve times

A parameter is a value you leave deliberately unfixed in the source, so that the same document can be rendered against different scopes. Declare them in the front matter:

params:
  depot: "DP01"
  quarter: "2026-Q1"

and override them at the command line:

quarto render report.qmd -P depot:DP05 -P quarter:2026-Q1 \
  --output depot-DP05-2026Q1.html

Everywhere the report refers to params$depot, it now means DP05, and every number, chart and exception list recomputes for that depot alone.

Wrap that in a loop over the twelve depot codes and one command produces twelve tailored reports, each with its own figures and its own exceptions. This is the point at which reproducible reporting stops being a tidiness virtue and becomes an obvious economic decision. Consider the arithmetic from the other direction: if assembling one depot report by hand takes a careful analyst half a day, twelve of them is six days of work, every quarter, before anybody has thought about what the numbers mean. The loop below is four lines and it runs while you make coffee.

depots <- c("DP01","DP02","DP03","DP04","DP05","DP06",
            "DP07","DP08","DP09","DP10","DP11","DP12")

walk(depots, \(d) quarto::quarto_render(
  "report.qmd", execute_params = list(depot = d, quarter = "2026-Q1"),
  output_file = glue::glue("depot-{d}-2026Q1.html")))

There is a second, quieter benefit. Because all twelve reports come from one source, a depot manager reading their own report and a regional director reading the roll-up are looking at the same definitions. The familiar situation where two managers arrive at a meeting with incompatible versions of their own availability figure simply cannot occur.

Freezing, so it renders on someone else’s machine

Some computations are slow — a model fit, a classification pass over every review in the file — and re-running them every time somebody rebuilds the site is both wasteful and a good way to make people stop rebuilding the site.

execute:
  freeze: auto     # re-run only when the source changes

freeze: auto tells Quarto to store the results of each code chunk and reuse them until the code that produced them changes. The document still renders from a single source; it simply does not repeat work it has already done.

For anything genuinely expensive, go one step further and take the computation out of the document altogether. Do it in a pipeline script that writes a small result file — a summary table of a few dozen rows rather than the whole raw extract — and have the document read that file. The document should be fast to render. This is not fastidiousness: if rendering your report takes twenty minutes, nobody will re-render it to check a change, and within two months somebody will start typing numbers again, for entirely understandable reasons.

The reproducibility standard, stated as a test

Can a colleague clone your folder onto a clean machine and produce your PDF?

That is the whole standard. It is the one every scientific journal, every regulator and every serious audit function is converging on, and it has the great merit of being testable in ten minutes rather than argued about in a policy document.

Three things usually break it. None of them is a sign of sloppy work — each is what happens when a script grows out of an interactive session, which is how nearly all analysis begins.

  1. Absolute paths. /Users/bongo/Desktop/data.csv exists on exactly one machine in the world. Use paths relative to the project root, so that the folder is portable.
  2. Packages installed interactively. The code works because you installed something six weeks ago and have forgotten. Record the dependencies — renv in R, a lockfile in Python — so the next person can install the same set.
  3. A manual step. “Then I open it in Excel and fix the header.” If it is not in the script, it does not exist, because it will not happen when you are on leave.

Core lab · 30 minutes

  • Write a two-page report on your capstone. Every number inline code. No typed figures.
  • Render it to HTML and PDF. Confirm the numbers match.
  • Change one thing in the pipeline. Re-render. Confirm every number moved.
  • Add a parameter and render the report twice for two different scopes.
  • Render to reveal.js and see what your report looks like as slides.
  • Hand the folder to the next table and have them render it on their machine.

That last step fails for about half the room on the first attempt, and it is designed to. The failure is nearly always one of the three items in the box above, it takes a few minutes to diagnose with somebody else’s error message in front of you, and it is very much better to find it here than to find it when a colleague inherits the report in nine months.

Stretch

Add a conditional paragraph — prose that appears only when the data warrants it.

```{r}
#| output: asis
if (availability < 0.95) {
  cat("::: {.callout-warning}\n",
      "Availability fell below the 95% floor in ", sum(breaches), " depot-weeks. ",
      "The service-level commitment to key accounts is at risk.\n:::\n")
}
```

Read that in English: if availability is below the floor, write this warning into the document; otherwise write nothing. The output: asis line tells Quarto to treat what the code prints as markdown rather than as program output, which is what allows the code to generate a formatted callout rather than a line of console text.

The report now escalates on its own. It raises the warning when the number crosses the threshold, and stays quiet when it does not — so nobody has to remember to check, and nobody has to remember to take the warning out again next month.

This is the beginning of the difference between a report and a monitoring system, and it costs six lines.

Copilot check

Assistants are excellent at this task. Describe your analysis and ask for a Quarto document and you will get a well-structured file with sensible sections, a working front matter block and code that runs.

There is one thing to check, every time: did it hard-code any numbers into the prose?

It usually will, and confidently. It sees the value 96.9% in the output you pasted and writes “availability was 96.9%” as ordinary text, because that is overwhelmingly what such a sentence looked like in everything it has read. It is not a lapse in reasoning; it is a very good imitation of how these documents are normally written, which is precisely the habit this session is trying to replace.

So search the source for digits appearing in prose, and replace every one with inline code. Then add this to your standing prompt, so you do not have to remember it again:

Every number that appears in prose must be inline code that computes it from the data. Do not hard-code any figure anywhere in the document text.

Takeaways

  1. The document contains the code that produces its own numbers. Nothing is typed.
  2. One source, five outputs, one command.
  3. Use a Word reference doc, and the corporate objection disappears.
  4. Parameterise, and twelve tailored reports cost the same as one.
  5. The standard: a colleague clones your folder onto a clean machine and gets your PDF.
