15  Security, privacy and governance

⚫ Master

What Classifying data, controlling who sees what, protecting personal data, managing secrets, and meeting the Nigeria Data Protection Act 2023
Why One leaked customer file costs more than the whole platform. Regulators (Nigeria Data Protection Commission (NDPC), Central Bank of Nigeria (CBN), National Pension Commission (PenCom), Nigerian Communications Commission (NCC)) increasingly ask how you govern data, not just whether you do
When Designed in from the first table holding personal data. Retrofitting is many times more expensive
Who The Data Protection Officer (DPO) sets policy. Owners classify. Engineers implement. Internal audit checks
Not legal advice

This chapter explains principles and engineering patterns. Regulations and directives change, and sector regulators add their own rules. Confirm current obligations with your DPO and legal counsel.

15.1 Classify first

Every table and column in the catalogue gets a classification. Controls follow from it:

Class Examples Controls
Public Published macro data, Harvard Dataverse sets None beyond integrity
Internal Depot sales, product lists Staff access; no external sharing
Confidential Salaries, margins, supplier prices Role-based access; logged queries; masked in non-production
Restricted / personal Names, phone numbers, Bank Verification Number (BVN), National Identification Number (NIN), Retirement Savings Account (RSA) personal identification numbers (PINs), health data, complaints text Minimise; pseudonymise; strict roles; data protection impact assessment (DPIA); retention limits; never to external artificial intelligence (AI) without a lawful basis and agreement

15.2 Find personal data automatically

🧠 Prompt 15.1 — a personally identifiable information (PII) scanner

Write a function that scans every VARCHAR column of every table in a DuckDB schema and flags columns where more than 5% of a sample of values look like Nigerian phone numbers, email addresses, 11-digit identifiers (possible BVN or NIN), or personal names from a short list. Output a classification suggestion per column for the steward to confirm.

# A small table with personal data mixed in (synthetic)
dbWriteTable(con, DBI::Id(schema = "bronze", table = "contacts"), data.frame(
  customer_id = sprintf("C%05d", 1:6),
  full_name   = c("Ada Okafor", "Musa Bello", "Ngozi Eze", "Tunde Bakare", "Aisha Sani", "Emeka Obi"),
  phone       = c("08031234567", "+2348099876543", "07012345678", "09087654321", "08022223333", "08177778888"),
  email       = c("ada@example.ng", "musa@example.ng", NA, "tunde@example.ng", "aisha@example.ng", "emeka@example.ng"),
  bvn         = c("22212345678", "22298765432", "22233334444", "22255556666", "22277778888", "22299990000"),
  segment     = c("Mass", "Affluent", "Mass", "SME", "Mass", "Affluent")))
bronze_ingest(con, "bank_customers.csv")

scan_pii <- function(con, schema = "bronze", n = 500) {
  cols <- dbGetQuery(con, "SELECT table_name, column_name FROM information_schema.columns WHERE table_schema = ? AND data_type = 'VARCHAR'", params = list(schema))
  patterns <- c(phone = "^(\\+?234|0)[789][01]\\d{8}$", email = "^[^@ ]+@[^@ ]+\\.[a-z]{2,}$", id_11_digits = "^\\d{11}$",
                person_name = "^[A-Z][a-z]+ [A-Z][a-z]+$")
  out <- lapply(seq_len(nrow(cols)), function(i) {
    v <- na.omit(dbGetQuery(con, sprintf('SELECT "%s" v FROM %s.%s USING SAMPLE %d', cols$column_name[i], schema, cols$table_name[i], n))$v)
    hits <- vapply(patterns, function(p) mean(grepl(p, v)), 0)
    if (max(hits) > .05) data.frame(table = cols$table_name[i], column = cols$column_name[i],
                                    detected = names(which.max(hits)), share = round(max(hits), 2), suggested_class = "Restricted / personal")
  })
  do.call(rbind, out)
}
scan_pii(con)
table column detected share suggested_class
contacts full_name person_name 1 Restricted / personal
contacts phone phone 1 Restricted / personal
contacts email email 1 Restricted / personal
contacts bvn id_11_digits 1 Restricted / personal

The scanner suggests. A steward confirms, and the confirmation is written to the catalogue.

15.3 Pseudonymise and mask

  • Pseudonymisation replaces an identifier with a consistent token. Analysts can still join and count, but can’t identify a person without the separately guarded key. (The pension employers file already does this: employer_name_hash.)
  • Masking shows partial values to roles that need to recognise, not read: 080******67.
salt <- Sys.getenv("PII_SALT", "demo-salt-store-me-in-a-vault")      # the secret that makes hashes irreversible in practice
run_sql(con, "silver", "contacts", sprintf("
  SELECT customer_id,
         sha256(%s || bvn)                                         AS bvn_token,      -- joinable, not reversible without the salt
         left(phone, 3) || '******' || right(phone, 2)             AS phone_masked,
         regexp_replace(email, '^(.).*@', '\\1***@')               AS email_masked,
         segment                                                   -- full_name dropped: not needed for analysis (minimisation)
  FROM bronze.contacts", sq(salt)))
dbGetQuery(con, "SELECT * FROM silver.contacts LIMIT 3")

15.4 Access control: least privilege, by role

Role Bronze Silver Gold Restricted columns Typical holders
Viewer — — via dashboards only — Managers, executives
Analyst — read read masked Analysts, data scientists
Engineer read/write read/write read/write pseudonymised Data team
Steward read read read read (for quality work) Named data stewards
Admin all all all all, with logging 1–2 people, break-glass

Row-level security limits which rows a role sees: a regional manager sees only their region. In PostgreSQL it is a policy:

ALTER TABLE analytics.fct_sales ENABLE ROW LEVEL SECURITY;
CREATE POLICY region_policy ON analytics.fct_sales
  USING (region = current_setting('app.user_region'));

In a Shiny dashboard on Posit Connect, session$user (and session$groups) identify the viewer. Filter in get_sales():

user_region <- lookup_region(session$user)        # from a gold.user_access table maintained by HR
sales <- reactive(get_sales(input$source, c(filters(), list(regions = user_region))))

15.5 Secrets

  • Never in code, Git, Quarto documents or screenshots.
  • On laptops: .Renviron (git-ignored), or the operating system (OS) keychain via the keyring package.
  • On servers: the platform’s secret store (GitHub Actions secrets, Azure Key Vault, Posit Connect variables).
  • Rotate on staff exit and at least yearly. Use service accounts for pipelines, not personal logins.

15.6 The NDPA 2023, in engineering terms

Principle (Nigeria Data Protection Act (NDPA) 2023) What it means for the platform
Lawful basis and purpose limitation Record the purpose of each personal-data table in the catalogue; don’t reuse it for an unrelated purpose without a new basis
Data minimisation Silver drops columns the purpose doesn’t need (we dropped full_name)
Accuracy The tests and steward process are your accuracy controls
Storage limitation Retention period per table, plus an automated purge job (below)
Integrity and confidentiality Classification, roles, encryption at rest and in transit, secrets management
Accountability DPIA for high-risk processing (AI on complaints, profiling); audit logs; a named DPO
Data subject rights Be able to find a person’s data (lineage + pseudonym keys) to answer access and erasure requests
Breach notification Detect (logs, alerts) and know whom to notify, and how fast, under the Act and the NDPC’s directives
Cross-border transfer Know where your cloud region and AI provider process data

The General Application and Implementation Directive (GAID) 2025 (the NDPC’s General Application and Implementation Directive) adds implementation detail, including DPIA and audit expectations. Sector regulators add more: CBN for banks, PenCom for pension operators, NCC for telecoms.

15.7 AI-specific governance

  • Data classes per model tier: public data to any model; internal data to an enterprise application programming interface (API) under a no-training agreement; restricted data to a local model (Ollama), or not at all.
  • Log prompts and outputs for AI features, and review samples monthly.
  • A human is accountable for every AI-assisted decision about a person (credit, hiring, claims).
  • Test for bias across groups: language (Pidgin vs English, Chapter 11), region, gender where lawful.

15.10 🏢 In the organisation

Invite the DPO and internal audit to the platform’s design review, not its launch. Show them the classification, the role matrix, the purge job and the logs. Platforms that do this pass audits in days. Platforms that don’t are often frozen for months.
