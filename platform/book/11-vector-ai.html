11  Vector search and AI on governed data

🟣 Advanced

What Turning text into vectors (“embeddings”) for search-by-meaning, and connecting large language models to the warehouse safely: retrieval-augmented generation (RAG) and text-to-Structured Query Language (SQL)
Why Most of an organisation’s knowledge is text: complaints, reviews, call notes, incident reports. And most users would rather ask a question than build a query
When After the semantic layer exists. Artificial intelligence (AI) without governed definitions just invents confident wrong answers faster
Who Analytics engineers build the index. The data protection officer (DPO) approves what data may reach which model. Users ask questions, and review the SQL

11.1 Embeddings in one picture

An embedding turns a piece of text into a list of numbers, a point in space, so that texts with similar meaning land close together. Cosine similarity measures closeness: 1 means the same direction, 0 means unrelated. A vector index stores these points and finds the nearest neighbours of a query quickly.

Embedding method How it works Strengths Weaknesses
Term frequency–inverse document frequency (TF-IDF) (in kit.R) Counts words, weights rare words up Free, offline, explainable, instant Matches words, not meaning; no synonyms; one language at a time
Neural sentence embeddings (e.g. all-MiniLM, multilingual-e5, OpenAI, Voyage) A trained model maps meaning to ~384–3072 dimensions Synonyms, paraphrase, cross-lingual (English ↔︎ Pidgin) Needs a model or application programming interface (API); costs; data-protection review

The English query finds the English complaints about non-remittance and misses the Pidgin complaints describing exactly the same problem. The Pidgin query finds them, because it shares the words “oga”, “pension” and “enter”. TF-IDF matches words, so it cannot know that “oga dey remove pension but e no enter” means “my employer deducts but does not remit”. A regulator relying on it would under-count the problem among Pidgin speakers. That is a fairness issue, not just a technical one.

The fix is a multilingual neural embedding model, and the swap touches one function, embed():

hf_embed <- function(texts, model = "intfloat/multilingual-e5-small") {
  httr2::request(paste0("https://router.huggingface.co/hf-inference/models/", model, "/pipeline/feature-extraction")) |>
    httr2::req_auth_bearer_token(Sys.getenv("HF_TOKEN")) |>
    httr2::req_body_json(list(inputs = texts)) |> httr2::req_perform() |>
    httr2::resp_body_json(simplifyVector = TRUE)
}

11.3 From search to themes: clustering

🧠 Prompt 11.2 — discover complaint themes

Cluster the complaint vectors into 8 themes with k-means. For each cluster, show its size, its most characteristic words, its share of Pidgin complaints and its average days to resolve. Name each theme in plain English.

m <- do.call(rbind, vecs$vec)

11.4 Retrieval-augmented generation (RAG)

An large language model (LLM) knows nothing about your complaints. RAG fixes that in three steps:

  1. Retrieve the most relevant records from the vector index.
  2. Augment the prompt with them.
  3. Let the model generate an answer that cites them.
🧠 Prompt 11.3 — a governed RAG prompt

Build a function that, for a question, retrieves the 8 most similar complaints and assembles a prompt instructing the model to answer only from those complaints, cite complaint identifiers (IDs), say “not enough evidence” if they don’t answer it, and never output personal data. Show the assembled prompt; call Claude only if ANTHROPIC_API_KEY is set.

rag_prompt <- function(question, k = 8) {
  hits <- vector_search(con, idx, question, k = k)
  context <- paste(sprintf("[%s | %s | %s] %s", hits$complaint_id, hits$channel, hits$language, hits$complaint_text), collapse = "\n")
  paste0("You are a pensions customer-experience analyst.\n",
         "Answer ONLY from the complaints below. Cite complaint IDs in brackets. ",
         "If they do not answer the question, say 'not enough evidence'. Never reveal personal data.\n\n",
         "COMPLAINTS:\n", context, "\n\nQUESTION: ", question)
}

ask_claude <- function(prompt, model = "claude-sonnet-5-5") {
  httr2::request("https://api.anthropic.com/v1/messages") |>
    httr2::req_headers(`x-api-key` = Sys.getenv("ANTHROPIC_API_KEY"), `anthropic-version` = "2023-06-01") |>
    httr2::req_body_json(list(model = model, max_tokens = 600, messages = list(list(role = "user", content = prompt)))) |>
    httr2::req_perform() |> httr2::resp_body_json() |> (\(r) r$content[[1]]$text)()
}
cat(ask_claude(rag_prompt("What are customers saying about updating their contact details?")))

11.5 Text-to-SQL, with guardrails

The Lab dashboard’s Ask your data page sends a question, plus the schema and the semantic-layer definitions (never the data rows), to a model that writes SQL. A human reviews the SQL, then it runs read-only. Each guardrail closes one specific risk:

Guardrail Risk it closes
Semantic layer in the system prompt The model inventing its own definition of “revenue”
Read-only connection + SELECT-only check Prompt injection that tries to DROP TABLE
Row cap (LIMIT 5000) Exfiltrating whole tables
SQL shown to the user before running Silent wrong answers
Only schema + definitions sent, not rows Personal data leaving the organisation (Nigeria Data Protection Act (NDPA))
Local model option (Ollama) Any data leaving the laptop at all
Question → SQL → result logging No audit trail
A golden-question test set Quality drifting when the model or prompt changes
🧠 Prompt 11.4 — evaluate text-to-SQL

Build a small evaluation harness: a table of golden questions, each with a reference SQL. For each candidate SQL (from any model), run both, compare the results (same rows and values within 0.1%), and report accuracy. Include one deliberately wrong candidate to prove the harness catches it.

golden <- data.frame(
  question = c("How many complaints are still open?",
               "Which channel receives the most complaints?",
               "Average days to resolve complaints received in 2025"),
  reference = c("SELECT COUNT(*) AS n FROM silver.complaints WHERE status = 'open'",
                "SELECT channel FROM silver.complaints GROUP BY 1 ORDER BY COUNT(*) DESC LIMIT 1",
                "SELECT round(AVG(days_to_resolve),1) AS d FROM silver.complaints WHERE year(received_date) = 2025"),
  candidate = c("SELECT COUNT(*) FROM silver.complaints WHERE status = 'open'",
                "SELECT channel FROM silver.complaints GROUP BY channel ORDER BY COUNT(*) DESC LIMIT 1",
                "SELECT round(AVG(days_to_resolve),1) FROM silver.complaints WHERE received_date >= DATE '2025-01-01'"))   # wrong: no upper bound, so 2026 is included
same <- function(a, b) isTRUE(all.equal(unname(as.list(a)), unname(as.list(b)), tolerance = 1e-3, check.attributes = FALSE))
golden$correct <- mapply(function(r, c) same(dbGetQuery(con, r), dbGetQuery(con, c)), golden$reference, golden$candidate)
golden[, c("question", "correct")]
question correct
How many complaints are still open? TRUE
Which channel receives the most complaints? TRUE
Average days to resolve complaints received in 2025 FALSE 
cat("Accuracy:", mean(golden$correct))
Accuracy: 0.6666667

The harness caught the subtle error. The candidate’s date filter has no upper bound, so it quietly includes 2026 complaints. This is exactly the kind of mistake that looks fine to a busy manager. Note also what the harness did not flag: both versions of the first question return the same count, even though one names its column n and the other doesn’t. The harness compares results, not wording.

11.7 ✅ Mastery check

  • Explain an embedding and cosine similarity to a board member in three sentences.
  • Name four guardrails for text-to-SQL and the risk each removes.
  • Why is a golden-question test set necessary even if the model “seems good”?
Solutions
  • Model answer: “An embedding turns a piece of text into a list of numbers, a point on a map, so that texts with similar meanings sit close together. Cosine similarity measures how closely two points point the same way: 1 means the same meaning, 0 means unrelated. That lets us search complaints by what they mean, not by the exact words used.”
  • Any four of: semantic layer in the prompt, so the model doesn’t invent definitions; read-only connection and a SELECT-only check, against prompt injection such as DROP TABLE; row cap, against exfiltrating whole tables; SQL shown before it runs, against silent wrong answers; only schema and definitions sent, never rows, against personal data leaving the organisation; a local model option, so no data leaves the machine; logging question → SQL → result, for an audit trail.
  • Because “seems good” is an impression from a few questions, and it changes silently whenever the model, the prompt or the schema changes. A golden-question set (questions with reference SQL whose results are compared automatically) turns quality into a number you can re-check after every change.

11.8 🏢 In the organisation

Before any AI feature goes live:

  • run a Data Protection Impact Assessment (NDPA 2023);
  • decide which data classes may reach which model (public API, enterprise API with no training on your data, or local model);
  • log every prompt and response;
  • name a human accountable for each AI-assisted decision.

The value is real (minutes instead of days to read 3,000 complaints), and so is the governance work it requires.
