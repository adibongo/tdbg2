12  Serving: trusted data where people work

🟣 Advanced

What Publishing gold (only after the gate) to the targets each audience uses: portable marts, shared databases, Power Platform, APIs and reports
Why People won’t come to the warehouse. The warehouse must go to them, without creating unofficial copies
When After every successful gate; on a schedule, never by hand
Who Analytics engineers publish. IT manages the shared servers. Owners decide who may see what

12.1 Choosing a serving target

Target Readers Writers Strengths Limits Use for
SQLite mart Excel (ODBC), Power BI, Python, any app none (read-only copy) One file, offline, universal Single writer; not for many concurrent users Finance packs, field teams, offline analysis
Parquet files Power BI, Fabric, Python, Spark, DuckDB none Tiny, fast, typed; partitionable Not a database (no permissions per row) Data science; lake storage; sharing with partners
PostgreSQL Many users and apps at once yes Real permissions, row-level security, APIs Needs a server and a DBA Multi-user apps, write-back forms, APIs
Microsoft Dataverse Power Apps, Power Automate, Dynamics, Power BI yes Security roles, Microsoft-native API limits; licence costs per user Microsoft-first organisations, field apps
Quarto + Shiny Anyone with a browser (optional write-back) Governed, interactive, branded Needs a host (Chapter 16) Executive and operational dashboards
REST API Other systems — Integration Engineering effort Feeding the CRM, mobile apps, partners
Quarto report (PDF/HTML) Board, regulator — Reproducible, signed-off, archived Static Board packs, regulatory returns

Rule: whatever the target, it is refreshed from gold by the pipeline, after the gate. No one hand-copies data into a serving target, because that is how shadow versions are born.

12.2 SQLite: the portable mart

🧠 Prompt 12.1 — publish a serving mart

After the tests pass, publish gold.dim_depot, gold.dim_product, gold.dim_week, gold.fct_sales and gold.mart_depot_month to a SQLite file, atomically (build to a temp file, then swap). Add a view in the SQLite file that pre-joins the star for Excel users. Then prove a reader sees the right totals.

Connecting Excel: install the SQLite ODBC driver, then Data → Get Data → From Other Sources → From ODBC and pick the DSN. Excel now refreshes from the mart instead of storing a pasted copy. Power BI: Get Data → ODBC, or connect to the DuckDB file directly with the DuckDB ODBC driver or Power Query connector.

12.4 PostgreSQL: the shared, multi-user target

pg <- dbConnect(RPostgres::Postgres(), host = Sys.getenv("PGHOST"), dbname = Sys.getenv("PGDATABASE"),
                user = Sys.getenv("PGUSER"), password = Sys.getenv("PGPASSWORD"))
dbExecute(pg, "CREATE SCHEMA IF NOT EXISTS analytics")
for (t in c("dim_depot", "dim_product", "fct_sales"))
  dbWriteTable(pg, DBI::Id(schema = "analytics", table = t), dbGetQuery(con, paste0("SELECT * FROM gold.", t)), overwrite = TRUE)
# Row-level security: each regional manager sees only their region (Chapter 15)
dbExecute(pg, "ALTER TABLE analytics.dim_depot ENABLE ROW LEVEL SECURITY")
dbDisconnect(pg)

DuckDB can also push directly with ATTACH 'postgres:…' AS pg; CREATE TABLE pg.analytics.fct_sales AS SELECT * FROM gold.fct_sales;. That is one statement with no R round-trip, which is faster for large tables.

12.5 Microsoft Dataverse: the Power Platform target

# Upsert monthly depot KPIs into a Dataverse table, keyed by an alternate key 'cr123_key'
rows <- dbGetQuery(con, "SELECT year_month || '|' || depot_code AS key, depot_name, revenue_ngn, stockout_rate FROM gold.mart_depot_month")
for (i in seq_len(nrow(rows)))   # use the $batch endpoint for >1,000 rows
  msdv_request(sprintf("cr123_depotkpis(cr123_key='%s')", rows$key[i])) |>
    httr2::req_method("PATCH") |>
    httr2::req_body_json(list(cr123_depotname = rows$depot_name[i], cr123_revenue = rows$revenue_ngn[i],
                              cr123_stockoutrate = rows$stockout_rate[i])) |> httr2::req_perform()

A Power App for depot managers can now show “your depot this month” from Dataverse, with security roles enforced by Microsoft. A Power Automate flow can email the manager when the stockout rate passes 5%.

12.6 An API for other systems

# plumber.R — serve governed metrics as JSON:  plumber::pr("plumber.R") |> plumber::pr_run(port = 8000)
#* Revenue and margin by region for a year
#* @param year:int
#* @get /kpis/region
function(year = 2025) {
  con <- DBI::dbConnect(duckdb::duckdb(), "_platform/retail.duckdb", read_only = TRUE)
  on.exit(DBI::dbDisconnect(con, shutdown = TRUE))
  DBI::dbGetQuery(con, metric_sql(layer, c("revenue", "gross_margin_pct"), dims = "region",
                                  where = sprintf("year = %d", as.integer(year))))
}

12.7 The serving contract

Treat each serving object like an API:

  • Stable names and columns. Breaking changes get a new version (v_sales_v2) and a retirement date for the old one.
  • Documented freshness. “Refreshed daily by 07:00 with data to last Sunday.”
  • Owner and support route in the catalogue.
  • Access defined by role, not by person (Chapter 15).

publish_all <- function(con, results) {
  if (!gate(results)) stop("Gate closed: nothing published.")
  publish_sqlite(con, c("gold.fct_sales", "gold.dim_depot", "gold.dim_product"), "_serving/retail_mart.sqlite"); log_event(con, "serve", "sqlite", 3, "ok")

  if (nzchar(Sys.getenv("PGHOST"))) log_event(con, "serve", "postgres", 0, "would publish")
  invisible(TRUE)
}

12.10 🏢 In the organisation

Count the unofficial copies of key data: spreadsheets emailed weekly, exports on shared drives. Each one is a future argument. Serving succeeds when those copies disappear because the official target is easier to use than the copy.
