2.2 A project layout that scales

Use one folder per platform, and the same layout every time:

my-platform/
├── config.yml           ← WHERE things are (paths, servers, schedules). Safe to share.
├── .Renviron            ← WHO you are (passwords, API keys). NEVER shared or committed.
├── .gitignore           ← lists .Renviron, data/db/, *.duckdb
├── R/                   ← reusable functions (kit.R, pipelines)
├── semantic/            ← metrics.yml — business definitions
├── data/raw/            ← sources exactly as received (read-only by convention)
├── data/db/             ← generated databases (rebuildable, so not backed up)
├── notebooks/*.qmd      ← exploration and teaching
├── dashboard.qmd        ← the Shiny dashboard
└── refresh.R            ← the scheduled pipeline

Three rules:

  1. Raw is read-only. Never edit a source file by hand. Fixes go into silver, as code.
  2. Generated means disposable. You must be able to delete data/db/ and rebuild it with one command.
  3. Config is not secrets. config.yml says where; .Renviron says who.

The R_CONFIG_ACTIVE environment variable selects the profile. The same code runs in development and production without editing.

Secrets go in .Renviron in the project folder:

PGPASSWORD=s3cret
ANTHROPIC_API_KEY=sk-...

…and are read with Sys.getenv("PGPASSWORD"). Restart R after editing it. In production, the same variables come from the server’s secret store (GitHub Actions secrets, Azure Key Vault, Posit Connect environment variables).

2.4 Your first warehouse query

🧠 Prompt 2.2 — hello, DuckDB

In R, create an in-memory DuckDB connection, run SQL directly on the CSV file fmcg_sell_out.csv without importing it, and show total revenue by year. Then do the same with dplyr on a lazy table and show me the SQL dplyr generated.

source("R/kit.R")
con <- dbConnect(duckdb())
dbGetQuery(con, sprintf("
  SELECT year(CAST(week_starting AS DATE)) AS year,
         round(SUM(revenue_ngn) / 1e9, 2)  AS revenue_bn,
         COUNT(*)                          AS rows
  FROM read_csv_auto('%s')
  GROUP BY 1 ORDER BY 1", raw_path("fmcg_sell_out.csv")))
year revenue_bn rows
2024 16.44 24456
2025 23.48 24752
2026 7.13 6266

The same question in dplyr. It is translated to SQL and runs inside DuckDB:

sales <- tbl(con, sql(sprintf("SELECT * FROM read_csv_auto('%s')", raw_path("fmcg_sell_out.csv"))))
q <- sales |> mutate(year = year(week_starting)) |> group_by(year) |>
  summarise(revenue_bn = sum(revenue_ngn, na.rm = TRUE) / 1e9, rows = n())
show_query(q)
<SQL>
SELECT "year", SUM(revenue_ngn) / 1000000000.0 AS revenue_bn, COUNT(*) AS "rows"
FROM (
  SELECT *, EXTRACT(year FROM week_starting) AS "year"
  FROM (SELECT * FROM read_csv_auto('/home/claude/shiny-dashboard-lab/data/raw/fmcg_sell_out.csv')) AS q01
) AS q01
GROUP BY "year"
collect(q)
year revenue_bn rows
2025 23.48137 24752
2024 16.44114 24456
2026 7.12907 6266 
dbDisconnect(con, shutdown = TRUE)
Why DuckDB as the warehouse?
  • It is free and has no server. It runs inside R or Python, so there is nothing to install or administer.
  • It is columnar. Aggregating 100 million rows on a laptop takes seconds.
  • It reads CSV, Parquet, JSON and Excel directly, and talks to PostgreSQL, SQLite and S3.
  • It speaks standard SQL, so the skills transfer to Snowflake, BigQuery and Fabric.
  • It graduates without a rewrite: MotherDuck is DuckDB in the cloud.

2.5 Version control in five commands

git init                          # once per project
git add R semantic *.qmd config.yml .gitignore
git commit -m "Add silver layer for sell-out"
git remote add origin https://github.com/your-org/my-platform.git
git push -u origin main

Commit code, configuration and definitions. Never commit data or secrets. Your .gitignore should contain at least:

.Renviron
data/db/
*.duckdb
*.sqlite
_book/

This raw answer is slightly wrong: the file has duplicate rows. You fix that in Chapter 7. That is exactly why gold exists.

E2.3. data/db/ is generated. Committing it bloats the repository, leaks data into Git history for ever (an NDPA risk), and causes merge conflicts on binary files. The code that rebuilds it is what gets versioned.

2.8 🏢 In the organisation

IT departments often block package installs on corporate laptops. Plan for it:

  • Ask IT for an approved R/Quarto image, or use Posit Cloud or GitHub Codespaces as a fallback.
  • Agree where secrets will live before the first connection to a production database. The answer should never be “in the script”.
