9  Tests and the publish gate

🔵 Practitioner

What Automated assertions about the data, run on every build. A gate publishes only if they pass
Why Because the most expensive data error is the one a director finds in a board pack. Tests turn silent errors into loud, early, cheap ones
When Every run, between gold and serving. Some also run on bronze (volume) and silver (validity)
Who Engineers write tests. Stewards set thresholds and severities. Owners receive the alerts

9.1 The eight tests that catch 90% of problems

Test Asserts Catches kit function
unique the declared grain holds double loads, fan-out joins t_unique()
not_null required fields are present broken extracts, failed casts t_not_null()
accepted_values codes are from a known list new, misspelt or unmapped codes t_accepted()
range numbers are plausible 31-hour days, negative stock, % stored as 0–100 vs 0–1 t_range()
relationships every foreign key exists in its dimension orphan facts, missing master data t_relationship()
freshness the latest data is recent enough a stalled feed nobody noticed t_fresh()
volume row counts are within expected bounds half a file, an empty delivery t_rowcount()
reconciliation totals agree with an authoritative source everything else, including logic errors t_custom()

Each test returns the number of failing rows. Zero means pass. Each has a severity:

  • error blocks publishing;
  • warn publishes, but alerts.

9.2 Run the suite

🧠 Prompt 9.1 — a test suite for gold

Write data tests for the retail gold layer: uniqueness of fct_sales at its grain and of each dimension key; not-null revenue; units ≥ 0; discount between 0 and 0.5; on_promotion in (0,1); fact-to-dimension relationships; at least 50,000 rows; freshness within 21 days of a given as-of date (warning only); and FY2025 revenue reconciling to the Excel regional report within 1% for every depot. Return a results table and log it.

# The suite is defined once, in R/retail.R, and reused by the scheduler
results <- run_tests(con, retail_tests(as_of = as.Date("2026-04-14")))
show_tests(results)
status severity test failing_rows
PASS error unique(gold.fct_sales: week_starting+depot_code+sku) 0
PASS error unique(gold.dim_depot: depot_code) 0
PASS error unique(gold.dim_product: sku) 0
PASS error not_null(gold.fct_sales.revenue_ngn) 0
PASS error range(gold.fct_sales.units_sold in [0, Inf]) 0
PASS error range(gold.fct_sales.discount_pct in [0, 0.5]) 0
PASS error accepted_values(gold.fct_sales.on_promotion) 0
PASS error relationship(gold.fct_sales.depot_code -> gold.dim_depot) 0
PASS error relationship(gold.fct_sales.sku -> gold.dim_product) 0
PASS error row_count(gold.fct_sales ≥ 50,000) 0
PASS warn freshness(gold.fct_sales ≤ 21 days) 0
PASS error reconcile: FY2025 regional report vs warehouse (±1%) 0 
cat("GATE:", if (gate(results)) "OPEN → publish" else "CLOSED → do not publish")
GATE: OPEN → publish
Why an as_of date?

Freshness depends on when you ask. The course data ends in March 2026, so we test as of mid-April 2026. In production, as_of = Sys.Date(). Making time a parameter is what makes the test itself testable.

9.3 Watch the gate close

The gate only earns trust if it actually stops bad data. Let’s break gold on purpose by re-loading a week of data twice, the most common real-world accident:

dbExecute(con, "CREATE OR REPLACE TABLE gold.fct_sales_backup AS SELECT * FROM gold.fct_sales")
[1] 55260
dbExecute(con, "INSERT INTO gold.fct_sales SELECT * FROM gold.fct_sales WHERE week_starting = DATE '2026-03-30'")
[1] 480
broken <- run_tests(con, retail_tests(as_of = as.Date("2026-04-14")))
show_tests(broken |> dplyr::filter(status != "PASS"))
status severity test failing_rows
FAIL error unique(gold.fct_sales: week_starting+depot_code+sku) 480 
cat("GATE:", if (gate(broken)) "OPEN" else "CLOSED → alert sent, yesterday's serving mart stays live")
GATE: CLOSED → alert sent, yesterday's serving mart stays live
dbExecute(con, "CREATE OR REPLACE TABLE gold.fct_sales AS SELECT * FROM gold.fct_sales_backup")
[1] 55260
dbExecute(con, "DROP TABLE gold.fct_sales_backup")
[1] 0

The uniqueness test caught it. Notice that the reconciliation test did not: one duplicated week in March 2026 doesn’t touch FY2025. That’s why you need several kinds of test. Each one sees a different failure.

9.4 Gate, then publish

publish_if_green <- function(con, results, tables, path) {
  if (!gate(results)) { log_event(con, "gate", "serving", 0, "BLOCKED"); return(invisible(FALSE)) }
  publish_sqlite(con, tables, path)
  log_event(con, "gate", "serving", length(tables), paste("published", basename(path)))
  invisible(TRUE)
}
publish_if_green(con, results, c("gold.dim_depot", "gold.dim_product", "gold.dim_week", "gold.fct_sales", "gold.mart_depot_month"),
                 "_platform/retail_serving.sqlite")
dbGetQuery(con, "SELECT run_at, layer, object, detail FROM ops.run_log WHERE layer = 'gate' ORDER BY run_at DESC LIMIT 3")
run_at layer object detail
2026-10-15 12:24:12 gate serving published retail_serving.sqlite

9.5 Test history is a quality KPI

run_tests() appends every result to ops.test_log. Over months, this log becomes the evidence of how reliable each source is:

dbGetQuery(con, "SELECT status, COUNT(*) AS results FROM ops.test_log GROUP BY 1 ORDER BY 1")
status results
FAIL 1
PASS 23

9.6 Designing good tests

  • Test the grain first. Uniqueness on the declared grain catches the most expensive errors.
  • Every business rule in silver gets a test in gold. “Blanks are stockouts” becomes “no null revenue”.
  • Reconcile to something outside the warehouse. Finance’s ledger, the regulator’s return, the bank statement. Internal consistency can’t prove accuracy.
  • Tune severity with the owner. A 0.5% reconciliation gap might be a warning in a weekly sales view and a hard failure in a regulatory return.
  • Keep tests fast. If the suite takes longer than the build, people will skip it.

9.7 🏋️ Exercises

E9.1 🟢 Add a test that gold.dim_depot has exactly 12 depots. Which kit function do you use?

E9.2 🟡 Write a test that compares the source’s on_time flag with the recomputed delivery_status in gold.fct_po_lifecycle, failing if they disagree on more than 2% of purchase orders (POs). Should it be error or warn?

E9.3 🔴 Write an anomaly test: fail if any depot’s revenue in the latest week is more than 3 standard deviations from its trailing 12-week mean. What are the risks of this kind of test?

Solutions 
extra <- list(
  t_custom("dim_depot has 12 depots", "SELECT abs(COUNT(*) - 12) FROM gold.dim_depot"),
  t_custom("latest-week revenue within 3σ of trailing 12 weeks", "
    WITH w AS (SELECT depot_code, week_starting, SUM(revenue_ngn) r FROM gold.fct_sales GROUP BY ALL),
         s AS (SELECT *, AVG(r) OVER win mu, stddev(r) OVER win sd FROM w
               WINDOW win AS (PARTITION BY depot_code ORDER BY week_starting ROWS BETWEEN 12 PRECEDING AND 1 PRECEDING))
    SELECT COUNT(*) FROM s WHERE week_starting = (SELECT MAX(week_starting) FROM w) AND abs(r - mu) > 3 * sd", sev = "warn"))
show_tests(run_tests(con, extra))
status severity test failing_rows
PASS error dim_depot has 12 depots 0
PASS warn latest-week revenue within 3σ of trailing 12 weeks 0

E9.1. Use t_custom(), because the expected count is a business fact rather than a generic rule. Alternatively, t_rowcount() with min 12, plus a uniqueness test.

E9.2. warn. A disagreement points to a data-entry or definition problem worth investigating, but it shouldn’t block the whole sales dashboard.

E9.3. Risks: (a) false alarms in seasonal weeks like Christmas and Ramadan, so compare with the same week last year; (b) small depots have high variance; (c) it is a warning signal, not proof of an error.

9.9 🏢 In the organisation

Tie the gate to a service level: “The sales dashboard refreshes by 07:00 with data to last Sunday. If tests fail, the Head of Commercial Finance is alerted by 06:30 and the previous version stays live.” That one sentence turns data quality from a technical worry into a managed commitment.
