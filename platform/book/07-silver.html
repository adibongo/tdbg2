7  Silver: clean, conform, remember

🔵 Practitioner

What The layer where raw data becomes true: typed, de-duplicated, standardised, conformed to shared codes, with history kept
Why So every cleaning decision is made once, in code everyone can read, instead of in every analyst’s spreadsheet
When After bronze, every run
Who Analytics engineers write it. Data stewards own the rules: which duplicate wins, what a blank means

7.1 The silver toolkit

Operation Question it answers SQL pattern
Type Is “2025-02-17” a date and “345.0” a number? CAST, TRY_CAST (null instead of error)
Standardise Are ” DP07” and “DP07” the same? trim, upper, regexp_replace
Interpret nulls What does a blank mean here? COALESCE + an evidence flag
De-duplicate Which of two identical rows survives? QUALIFY row_number() OVER (PARTITION BY key ORDER BY …) = 1
Conform Are SUP-CEDAR and SUP-CEDAR-NG one supplier? mapping table + join
Keep history What was the depot called last year? Slowly Changing Dimension type 2
Quarantine What do we do with rows that can’t be fixed? *_rejects table + test

7.2 Products and sell-out

🧠 Prompt 7.1 — the silver sell-out table

Write DuckDB SQL that builds silver.sell_out from bronze.fmcg_sell_out (all VARCHAR). Cast every column to its proper type. Treat blank units_sold and revenue_ngn as 0, because a blank means a stockout week (rule from the board pack Notes sheet), but keep a boolean units_was_blank as evidence. Keep exactly one row per (week_starting, depot_code, sku), preferring the earliest-loaded row. Comment every business rule.

This is the reviewed SQL, the same string the production script R/retail.R runs:

CREATE OR REPLACE TABLE silver.sell_out AS 
SELECT CAST(week_starting AS DATE)                      AS week_starting,
       trim(depot_code)                                 AS depot_code,
       trim(sku)                                        AS sku,
       COALESCE(TRY_CAST(units_sold  AS DOUBLE), 0)     AS units_sold,
       TRY_CAST(unit_price_ngn AS DOUBLE)               AS unit_price_ngn,
       CAST(on_promotion  AS INTEGER)                   AS on_promotion,
       CAST(discount_pct  AS DOUBLE)                    AS discount_pct,
       CAST(stockout_flag AS INTEGER)                   AS stockout_flag,
       COALESCE(TRY_CAST(revenue_ngn AS DOUBLE), 0)     AS revenue_ngn,
       units_sold IS NULL                               AS units_was_blank   -- keep the evidence
FROM bronze.fmcg_sell_out
-- one row per business key: exact duplicates AND conflicting re-sends collapse to the first load
QUALIFY row_number() OVER (PARTITION BY week_starting, depot_code, sku ORDER BY rowid) = 1
CREATE OR REPLACE TABLE silver.products AS 
SELECT trim(sku)                         AS sku,
       trim(product_name)                AS product_name,
       trim(category)                    AS category,
       pack_size,
       CAST(unit_cost_ngn  AS DOUBLE)    AS unit_cost_ngn,
       CAST(list_price_ngn AS DOUBLE)    AS list_price_ngn
FROM bronze.fmcg_products
QUALIFY row_number() OVER (PARTITION BY trim(sku) ORDER BY rowid) = 1

Prove what changed between bronze and silver:

WITH c AS (
  SELECT (SELECT COUNT(*) FROM bronze.fmcg_sell_out)                  AS bronze_rows,
         (SELECT COUNT(*) FROM silver.sell_out)                       AS silver_rows,
         (SELECT COUNT(*) FROM silver.sell_out WHERE units_was_blank) AS stockout_blanks_kept_as_evidence)
SELECT bronze_rows, silver_rows, bronze_rows - silver_rows AS duplicates_removed, stockout_blanks_kept_as_evidence FROM c
1 records
bronze_rows silver_rows duplicates_removed stockout_blanks_kept_as_evidence
55474 55260 214 786
“Which duplicate wins?” is a business decision

Of the duplicate keys, 211 are exact copies and 3 conflict (same key, different numbers). We keep the earliest-loaded row. The alternative, “latest wins”, is right when sources send corrections. The steward decides; the code records the decision. Write the rule in a comment, and test it (Chapter 9).

7.3 Slowly Changing Dimensions: remembering history

The depot master lists DP04 twice: “Abuja Central”, and later “Abuja Central (Wuse II)”. The regional report’s footnote explains it: “Abuja Central includes Wuse II from Q3.” This is a slowly changing dimension: an attribute that changes rarely, but whose history matters.

SCD type Behaviour Use when
Type 0 Never change Original attributes (date opened)
Type 1 Overwrite: only the current value survives Typos and corrections; history is not meaningful
Type 2 Add a new row with valid_from / valid_to / is_current History matters: reorganisations, renames, price lists, an employee’s grade
🧠 Prompt 7.2 — SCD type 2

bronze.fmcg_depots lists DP04 twice (a rename). Build silver.depot_history as an SCD type 2 table: one row per depot version, ordered by load order, with valid_from (the opened date for version 1; 2025-10-01 for later versions, per a business confirmation), valid_to (the day before the next version starts) and is_current.

CREATE OR REPLACE TABLE silver.depot_history AS 
-- Slowly Changing Dimension type 2: keep every version of a depot.
-- Business rule (confirmed by Commercial): the DP04 rename took effect 2025-10-01.
WITH d AS (
  SELECT trim(depot_code) AS depot_code, trim(depot_name) AS depot_name,
         trim(region) AS region, trim(state) AS state, CAST(opened AS DATE) AS opened,
         row_number() OVER (PARTITION BY trim(depot_code) ORDER BY rowid) AS version
  FROM bronze.fmcg_depots
), v AS (
  SELECT *, CASE WHEN version = 1 THEN opened ELSE DATE '2025-10-01' END AS valid_from FROM d
)
SELECT depot_code, version, depot_name, region, state, opened, valid_from,
       lead(valid_from) OVER (PARTITION BY depot_code ORDER BY version) - INTERVAL 1 DAY AS valid_to,
       lead(valid_from) OVER (PARTITION BY depot_code ORDER BY version) IS NULL         AS is_current
FROM v
SELECT * FROM silver.depot_history WHERE depot_code = 'DP04'
2 records
depot_code version depot_name region state opened valid_from valid_to is_current

DP04 2 Abuja Central (Wuse II) North Central FCT 2015-06-30 2025-10-01 NA TRUE

Now a sale in March 2025 can be reported under the name the depot had at the time, or under today’s name, whichever the question needs:

SELECT h.depot_name AS name_at_time_of_sale, SUM(s.revenue_ngn) / 1e9 AS revenue_bn
FROM silver.sell_out s
JOIN silver.depot_history h
  ON s.depot_code = h.depot_code
 AND s.week_starting BETWEEN h.valid_from AND COALESCE(h.valid_to, DATE '9999-12-31')
WHERE s.depot_code = 'DP04'
GROUP BY 1

7.4 Tidy the presentation spreadsheet in SQL

The same Excel clean-up you did in R in Chapter 3, done in SQL inside the warehouse. The steps are: fill the merged cells, drop the total and footnote, unpivot the months, and parse the naira text.

CREATE OR REPLACE TABLE silver.regional_report AS 
-- The printed Excel report, made tidy: fill merged region cells, unpivot months, parse '₦1,234'
WITH filled AS (
  SELECT last_value(region IGNORE NULLS) OVER (ORDER BY rowid) AS region, depot, * EXCLUDE (region, depot)
  FROM bronze.regional_report
  WHERE depot IS NOT NULL AND depot <> 'All depots'      -- drop the printed total and the footnote rows
), long AS (
  UNPIVOT filled ON Jan, Feb, Mar, Apr, May, Jun, Jul, Aug, Sep, Oct, Nov, Dec
  INTO NAME mon VALUE revenue_txt
)
SELECT region, depot AS depot_name,
       strptime('2025 ' || mon || ' 01', '%Y %b %d')::DATE                  AS month,
       CAST(regexp_replace(revenue_txt, '[^0-9.]', '', 'g') AS DOUBLE)       AS revenue_ngn
FROM long
SELECT * FROM silver.regional_report ORDER BY depot_name, month LIMIT 4
4 records

Two codes for one real-world thing break every total. The fix is a mapping table owned by the steward, versioned in Git and joined in silver:

🧠 Prompt 7.3 — conform supplier codes

supply_chain_pos.csv has SUP-CEDAR and SUP-CEDAR-NG, which procurement confirms are the same supplier. Create a small mapping table (source_code → conformed_code, reason, approved_by) and build silver.purchase_orders with a conformed supplier_id. Show on-time delivery % before and after conforming.

supplier_map <- data.frame(
  source_code    = c("SUP-CEDAR-NG"),
  conformed_code = c("SUP-CEDAR"),
  reason         = "Nigerian subsidiary of Cedar Ltd; same contract (Procurement, 2026-02)",
  approved_by    = "Head of Procurement")
dbWriteTable(con, DBI::Id(schema = "silver", table = "map_supplier"), supplier_map, overwrite = TRUE)
bronze_ingest(con, "supply_chain_pos.csv", system = "erp_procurement")
run_sql(con, "silver", "purchase_orders", "
  SELECT po_id, CAST(po_date AS DATE) AS po_date, CAST(received_date AS DATE) AS received_date,
         p.supplier_id AS supplier_id_source,
         COALESCE(m.conformed_code, p.supplier_id) AS supplier_id,
         material_group, CAST(order_value_ngn AS DOUBLE) AS order_value_ngn,
         CAST(on_time AS INTEGER) AS on_time,
         CAST(received_date AS DATE) < CAST(po_date AS DATE) AS date_error   -- flag, don't drop
  FROM bronze.supply_chain_pos p
  LEFT JOIN silver.map_supplier m ON p.supplier_id = m.source_code")
dbGetQuery(con, "SELECT supplier_id_source, supplier_id, COUNT(*) pos, round(AVG(on_time), 3) on_time
                 FROM silver.purchase_orders WHERE supplier_id = 'SUP-CEDAR' GROUP BY ALL")

7.6 Quarantine: rows you cannot fix

Some rows are simply wrong, like a 31-hour day. Don’t delete them and don’t let them through. Quarantine them: move them into a _rejects table with a reason, and let a test watch the reject count.

bronze_ingest(con, "energy_production_daily.csv", system = "scada_historian")
rules <- "CAST(uptime_hrs AS DOUBLE) BETWEEN 0 AND 24"
run_sql(con, "silver", "production_daily",         sprintf("SELECT * EXCLUDE (_source_file, _source_system, _loaded_at) FROM bronze.energy_production_daily WHERE %s", rules))
run_sql(con, "silver", "production_daily_rejects", sprintf("SELECT *, 'uptime_hrs outside 0-24' AS reject_reason FROM bronze.energy_production_daily WHERE NOT (%s)", rules))
dbGetQuery(con, "SELECT (SELECT COUNT(*) FROM silver.production_daily) kept, (SELECT COUNT(*) FROM silver.production_daily_rejects) quarantined")
kept quarantined
19667 37

The rejects go back to the source owner (here, the production engineers) with a request to fix the historian feed. The fix belongs at the source, not in silver.

7.9 🏢 In the organisation

Silver is where most of the organisation’s tacit knowledge becomes explicit. “We know Kaduna’s November data is off because of the re-segmentation” becomes a commented rule. Hold a monthly 30-minute data stewardship review: new anomalies, proposed rules, approvals. Minute it in the Git commit message.
