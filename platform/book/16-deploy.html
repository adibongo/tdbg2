16  Deploying in an organisation

⚫ Master

What Taking the platform from a laptop to a service an organisation relies on: environments, release process, hosting, people, rollout and growth
Why Most analytics initiatives fail at this stage, not on technology, but on ownership, adoption and the move into production
When When the first gold table has a business owner willing to stop using their spreadsheet
Who The head of data or analytics, with an executive sponsor, IT, the DPO and business owners

16.1 From laptop to service: three environments

Environment Purpose Data Who can change it
Development Build and try Samples or masked copies Any engineer, on a Git branch
Test / staging Prove a change before release Production-like, masked CI pipeline only
Production What the business uses Real Release process only. No hand edits, ever

The same code runs in all three. Only config.yml and secrets change, selected by R_CONFIG_ACTIVE (Chapter 2).

16.2 The release process (CI/CD)

A minimal GitHub Actions workflow that runs the data tests on every pull request:

# .github/workflows/ci.yml
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: r-lib/actions/setup-r@v2
      - uses: quarto-dev/quarto-actions/setup@v2
      - run: Rscript -e 'install.packages(c("DBI","duckdb","RSQLite","dplyr","readxl","yaml","config","knitr"))'
      - run: Rscript -e 'source("R/kit.R"); source("R/retail.R"); con <- platform_connect(fresh = TRUE); retail_build(con); r <- run_tests(con, retail_tests()); print(r); if (!gate(r)) quit(status = 1)'

16.3 Hosting options

Option What runs there Rough cost* Strengths Watch out for
Posit Connect Cloud Shiny/Quarto dashboards, scheduled reports free tier → paid plans Fastest path; Git-based deploys Data residency; private data needs a paid plan
shinyapps.io Shiny apps free tier → paid plans Simple Same as above
Posit Connect (self-hosted) Dashboards, APIs, schedules, SSO enterprise licence SSO, groups, row-level access, audit Licence and admin effort
A Linux VM (Azure, AWS, local data centre) Pipeline + Shiny Server + PostgreSQL a VM plus admin time Full control; data stays in-country if needed You patch and secure it
Microsoft Fabric / Power BI Lakehouse, pipelines, semantic models, reports capacity licence Fits Microsoft-first organisations Different toolchain; keep the design from this book
MotherDuck DuckDB in the cloud usage-based Same SQL; share one warehouse Newer; review data residency

*Check current pricing. It changes often, and Naira-denominated budgets need FX-risk allowances.

Data residency: some regulators expect certain data to stay in Nigeria, or require approval to move it. Check with the DPO and your sector regulator before choosing a cloud region.

16.4 People: the operating model

Model How it works Fits
Centralised One data team builds everything Small and mid-sized organisations; the first 12–18 months
Hub-and-spoke The central team owns the platform, standards and shared gold; embedded analysts in each business unit build their own marts Most mid-to-large organisations
Federated / data mesh Domains own their data products end to end, on a shared platform Large, mature organisations with strong domain teams

16.4.1 Who does what (RACI)

Activity Exec sponsor Business owner Steward Data team IT DPO
Define a KPI I A R C
Cleaning rules (silver) A R R
Build pipelines and gold C C A/R C
Test thresholds and severity A R R
Access roles A C R R C
Personal-data processing and DPIA C C R C A
Infrastructure, backups, patching C A/R
Fund and unblock A I I

R = responsible, A = accountable, C = consulted, I = informed.

16.5 The 30-60-90-day rollout

Phase Goal Deliverables Success looks like
Days 1–30: Prove One painful report, automated and trusted Bronze→gold for one subject area; 10 tests; semantic layer v1 (5–10 metrics); one dashboard; daily schedule The owner stops building the spreadsheet by hand
Days 31–60: Harden Make it a service Gate + alerts; runbook; roles and masking; DPIA if personal data; staging environment; CI One month at the SLA; the first failure caught by the gate, not by a director
Days 61–90: Expand Second and third subject areas, plus adoption Conformed dimensions; serving to Excel/Power BI/Dataverse; training for 20 users; dashboard census Two business units use certified metrics; unofficial copies start disappearing

16.6 Change management

  • Pick the first use case for pain, not glamour. The monthly report that eats three analysts’ week beats an AI demo.
  • Find a champion in each business unit, someone respected, who presents their numbers from the platform.
  • Retire the old way on purpose. Announce the date the emailed spreadsheet stops.
  • Teach the reading skill, not just the tool: what a test result means, what “certified” means, how to read a definition.
  • Celebrate caught errors. When the gate blocks bad data, tell the story. It is the platform’s best advertisement.

16.7 Measuring the platform itself

Platform KPI Target (year 1)
Refreshes meeting SLA ≥ 95% of days
Wrong numbers reaching a decision forum 0
Certified metrics in use 30–50
Active dashboard users per month growing; > 60% of intended audience
Unofficial copies retired count them; aim for every major one
Time to answer a new business question from days to hours
Cost per active user per month falling

16.8 Common failure patterns

Pattern Symptom Prevention
Dashboard-first 200 dashboards, no agreement Semantic layer before visuals (Chapter 10)
No owner “IT’s numbers are wrong” Every gold table and metric has a business owner
Hero pipeline Only one person can fix it Runbooks, code review, two people on-call
Tool shopping Licences bought, nothing used Prove value on DuckDB first; buy when a graduation trigger fires
Governance theatre Policies nobody follows Controls as code: tests, roles, purge jobs
AI before data A confident chatbot with wrong answers Gate + semantic layer + golden-question tests first

16.11 🏢 In the organisation

The architecture is easy to copy; the operating model is not. Organisations that succeed treat data as a product, with owners, users, a service level and a roadmap, rather than as a by-product of IT systems.
