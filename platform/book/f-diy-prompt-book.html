Appendix F — DIY prompt book: from your raw data to a live dashboard

This appendix is a hands-on, do-it-yourself guide. You have data of all sorts in your organisation: spreadsheets on shared drives, exports from an enterprise resource planning (ERP) system, a customer relationship management (CRM) database, a web service or two. You want a live, interactive dashboard that people trust. This prompt book takes you there in fourteen stages. Each stage gives you:

  • 🎯 the goal, in one sentence;
  • 🧠 the prompt to paste into your artificial intelligence (AI) assistant, with [[placeholders]] for your details;
  • ▶ the command to run;
  • ✔ the check: what you should see, and how to tell it worked;
  • 📗 the reference answer for a practice organisation, folded so you try first;
  • 💾 the commit: the point at which to save your work in Git.

It is built on a starter kit: a ready-made project folder in which every layer of the architecture already works. You don’t write a pipeline engine or a dashboard from scratch. You write the parts that are specific to your organisation: what the data means, how to clean it, what to measure. Those are exactly the parts an AI assistant can help with, and that a person must check.

Download the starter kit first

⬇ diy-starter-kit.zip, about one megabyte. Unzip it, rename the my-analytics folder to your project’s name, and open that folder in Positron or RStudio. It contains the engine, the dashboard, templates for every file you will write, and a complete practice organisation with its data and reference answers.

F.1 How to use this prompt book

F.1.1 The loop at every stage

  1. Prompt. Start every AI session with the session primer (below), then the stage’s prompt. Attach ai_context.md, which the kit rewrites on every run. It describes every table (columns, types, null %, ranges) without sending a single full record.
  2. Paste the answer into the file the prompt names. The AI writes files; you place them.
  3. Run the stage. Every run starts again from the raw data, so you can run as often as you like.
  4. Check against the stage’s ✔ list. If something is wrong, paste the error or the surprising number back to the AI with “this is what I got; what is wrong?”.
  5. Commit when the check passes, so you can always go back.

F.1.2 Rehearse on the practice organisation first

The kit includes Trans-Sahel Distribution Ltd, the book’s running example. It has sources in every shape you will meet: a comma-separated values (CSV) sell-out file with re-sent rows, a “presentation” Excel report, a JavaScript Object Notation (JSON) export, a database and a web application programming interface (API) (see practice/README.md).

Rscript use_practice.R answers   # load the practice data AND the reference answers
Rscript run_pipeline.R           # build it
quarto serve dashboard.qmd       # see the finished dashboard (10 minutes, start to finish)

Then start again in a fresh copy of the kit with Rscript use_practice.R (data only), and work through the stages yourself. Compare with the folded reference answers as you go. When that feels routine, do it with your own data.

F.2 The session primer (paste at the start of every AI session)

AI assistants forget everything between sessions. This primer tells the assistant what the kit is, what it may assume and how to answer. Paste it first, every time, then attach ai_context.md.

🧠 Prompt F0 — session primer

I am building a governed analytics platform with a starter kit. Data flows one way: files and systems land in bronze (DuckDB, every column as delivered, with lineage columns _source_file, _row and _loaded_at); Structured Query Language (SQL) files in sql/silver/ clean and type them; SQL files in sql/gold/ model them for decisions; tests/tests.yml holds data tests that must pass before anything is published; semantic/metrics.yml defines every metric once, and a Quarto + Shiny dashboard reads only those definitions.

The attached ai_context.md describes every table: columns, types, null %, approximate distinct counts and ranges. It is all you know about the data. Never invent a table or a column that is not in it; if you need one, say so.

When you write code: use DuckDB SQL; return complete files, each starting with a comment giving its path (for example -- sql/silver/03_sell_out.sql); use CREATE OR REPLACE TABLE (or VIEW); comment every business rule in plain English; and finish with the assumptions you made and the questions I should ask a data owner. If my request is ambiguous, ask me before writing code. My organisation: [[one line: who you are and what the dashboard is for]].

F.3 Stage 0 · Install your workbench

🎯 Goal: R, Quarto, an editor and Git installed, and the kit’s checks all OK.

  1. Install R (4.3 or newer) from cran.r-project.org, Quarto from quarto.org, and Git from git-scm.com.
  2. Install an editor: Positron (positron.posit.co) or RStudio. Positron includes an AI assistant pane; any assistant you are allowed to use works.
  3. Unzip the starter kit, rename the folder, open it in the editor and, in its terminal, run:
Rscript 00_setup.R
🧠 Prompt F0.1 — fix an installation problem

I am setting up R and Quarto on [[Windows 11 / macOS 14 / Ubuntu 24.04]], on a [[company-managed / personal]] laptop [[behind a proxy / without admin rights]]. Running Rscript 00_setup.R gave this output: [[paste the output]]. Explain what is wrong in plain language and give me the exact steps to fix it, one at a time, without needing admin rights if possible.

✔ Check. Every line of the --- checks --- block says OK. (The optional database drivers matter only if you will pull from PostgreSQL, SQL Server or Oracle.)

💾 Commit. git init, then git add -A and git commit -m "Start from the DIY starter kit". The kit’s .gitignore already keeps data, secrets and generated files out of Git.

F.4 Stage 1 · Create the project and write the brief

🎯 Goal: one page that says who the dashboard is for, which decisions it supports, and which numbers matter.

Most dashboard projects fail here, not in the code. A clear brief tells you which sources you need, what “correct” means, and when you are done. The kit copies brief.md to the top of ai_context.md, so every later prompt knows your situation.

🧠 Prompt F1 — interview me for the brief

Interview me to fill in brief.md for a dashboard project. Ask me one question at a time and wait for my answer: the organisation and unit; the decisions the dashboard must support (and how often they are made); the audience; the three to six numbers that matter, each with the person who owns its definition; the breakdowns people ask for; the time grain; the authoritative totals the numbers must reconcile to (for example a finance report); and whether any personal data is involved. Push back if a “number that matters” has no owner or no decision attached to it. At the end, write the complete brief.md in the same bullet format as the template I paste below. [[paste the brief.md template]]

Then set your project’s name in config.yml (project:) and the title at the top of dashboard.qmd.

✔ Check. Every line of brief.md is filled in. Each key number has an owner and a decision. You can name the report you will reconcile to. If personal data is involved, set ai_context_samples: false in config.yml now (Stage 13 explains why).

F.5 Stage 2 · Land your files in bronze

🎯 Goal: every file the dashboard needs, loaded into bronze exactly as delivered, with lineage.

  1. Collect exports, don’t edit them. Ask each owner for the regular export (the one that could be produced again next month), not a hand-tidied copy. Keep originals as they arrive.
  2. Drop them into data/raw/, one sub-folder per source (for example data/raw/sales/, data/raw/finance/). The kit reads CSV, tab-separated values (TSV), Excel (every sheet), Parquet and JSON.
  3. Only what the brief needs. If a file holds personal data the brief doesn’t need, ask for an export without those columns. That is data minimisation, and it is easier than deleting later.
  4. Run:
Rscript run_pipeline.R --to=bronze

Each file becomes one table, bronze.<file name> (an Excel workbook with several sheets gives one table per sheet, bronze.<file>__<sheet>), and the run lists each with its row count. Open ai_context.md to see what landed.

Spreadsheets made for printing usually land wrongly the first time: title rows become the header, so columns are called ...2 and ...3. Fix that with read options in sources.yml, not by editing the file.

🧠 Prompt F2 — fix how files were read

[[Session primer, then attach ai_context.md.]] Look at every bronze table. Which ones look as if they were read wrongly: a title row used as the header (columns named like ...2), the wrong delimiter (everything in one column), a broken encoding (â‚¦ instead of ₦), several tables on one sheet, or notes rows mixed with data? For each, write the files: entry for sources.yml that fixes it (options: skip, header, delim, encoding, sheets, table, skip_file), and tell me what to ask the owner if the file cannot be fixed by read options alone.

✔ Check.

  • Every file you dropped in appears in the run output with a sensible row count. (Compare with the row count you see when you open the file.)
  • Column names in ai_context.md match the files’ real headers.
  • ERROR lines name a file and a reason: fix the read option or ask for a cleaner export.
📗 Reference answer (practice organisation)

Finance’s regional report has four title rows above the header, so it needs skip: 4. The other files land correctly as they are. The files: section of sources.yml (full file in Stage 3):

  "finance/regional_report.xlsx":

F.6 Stage 3 · Connect databases and web APIs

🎯 Goal: system data pulled straight from the source, on every run, with no manual exports.

sources.yml lists databases (SQLite, DuckDB, PostgreSQL, and SQL Server, Oracle or others through Open Database Connectivity (ODBC)) and web APIs (JSON or CSV). Passwords and tokens go in .Renviron; sources.yml only holds the names of those variables. API responses are cached, so a failed call falls back to the last good copy.

Asking information technology (IT) for access: what to request

A read-only account; access to a view or a reporting replica rather than live production tables; the host, port, database name and driver; and the time window when queries are allowed. Ask for exactly the tables in your brief. You are much more likely to get a quick yes.

🧠 Prompt F3 — write the source entries

[[Session primer.]] Write sources.yml entries for these sources. Database: [[system name, e.g. our SQL Server ERP]], driver [[sqlite / postgres / odbc]], connection facts [[host, port, database, data source name (DSN), without any password]], and I need [[tables or a query: e.g. invoices since 2024 with these columns…]]. Web API: [[uniform resource locator (URL) and documentation link]], authentication [[none / API key in a header / bearer token]], response format [[JSON / CSV]]. Reference every secret by a variable name for .Renviron and show me the .Renviron lines with empty values. If a query could pull millions of rows, add a date filter and tell me why.

Then fill in .Renviron (restart R after editing) and run Rscript run_pipeline.R --to=bronze again.

✔ Check. Each source appears as bronze.<name>_<table> with a row count you can confirm with the system owner. Re-run it: the counts are the same, because every run rebuilds from the sources. No password appears in any file you would commit (git status should not list .Renviron).

F.7 Stage 4 · Profile before you trust

🎯 Goal: a written list of every data problem, with the rule that fixes it and the person who must agree to that rule.

This stage writes no code. It’s the conversation that makes silver possible. The AI spots patterns in ai_context.md; the data owners decide what they mean.

🧠 Prompt F4 — the issues log

[[Session primer, then attach ai_context.md.]] Profile every bronze table against the six quality dimensions: completeness, uniqueness, validity, consistency, timeliness and accuracy. Look especially for: likely duplicate keys; blanks that might mean something (zero, not applicable, still open); numbers or dates stored with symbols or in mixed formats; codes that differ between tables for the same thing; one entity appearing twice (a rename, a merger, two spellings); periods that don’t overlap between sources; and columns that could leak an outcome. Write docs/issues.md as a table: table, column, issue, evidence from ai_context.md, proposed rule, who must confirm it. Then list the SQL checks I should run to confirm each suspicion.

Run the suggested checks (in Positron, open data/db/dev.duckdb with the database pane, or in R DBI::dbGetQuery()), then take the issues log to the owners. Their answers become the comments in your silver SQL.

✔ Check. Every issue has evidence and an owner. Every rule that changes a number (for example “blank units mean a stockout, so 0”) has been confirmed by that owner, in writing.

F.8 Stage 5 · Silver: clean, type and conform

🎯 Goal: one silver table per real-world thing, typed and cleaned by written, agreed rules.

Write one SQL file per silver table, numbered in the order they must run (01_depots.sql, 02_products.sql, …). Each file reads only bronze (or earlier silver) tables.

🧠 Prompt F5 — a silver table

[[Session primer, then attach ai_context.md and docs/issues.md.]] Write sql/silver/[[NN]]_[[name]].sql that creates silver.[[name]] from bronze.[[table]]. Rules: cast every column to its proper type (use TRY_CAST where values may be dirty and say what becomes null); trim text and standardise codes; apply these agreed rules from the issues log: [[list them]]; keep exactly one row per [[business key]], preferring the first row loaded (QUALIFY row_number() OVER (PARTITION BY ... ORDER BY _row) = 1); keep an evidence flag wherever a rule changes a value; [[if history matters: build a type 2 history with valid_from, valid_to, is_current]]; [[if some rows can’t be fixed: put them in silver.[[name]]_rejects with a reason column, instead of dropping them]]. Comment each rule with who agreed it. Afterwards, give me two SQL queries that prove the rules worked.

Rscript run_pipeline.R --to=silver

✔ Check.

  • Each file runs (ok) and the run lists the silver table it created with a row count.
  • Row counts make sense: silver = bronze − duplicates − quarantined rows. Write the arithmetic down.
  • The two proof queries from the prompt return what you expect (for example, zero duplicate keys).
  • An error stops the run and names the file and line. Paste it back to the AI.
📗 Reference answer (practice organisation)

Five files. The sell-out table shows the typical pattern:

practice/sql/silver/03_sell_out.sql
-- silver.sell_out: typed weekly sell-out, one row per week x depot x SKU.
-- Rule (board pack Notes sheet): a blank units_sold means a stockout week -> 0, and we keep the evidence flag.
-- Rule: re-sent rows for the same key collapse to the first one loaded (214 duplicate keys in the source).
CREATE OR REPLACE TABLE silver.sell_out AS
SELECT CAST(week_starting AS DATE)                  AS week_starting,
       trim(depot_code)                             AS depot_code,
       trim(sku)                                    AS sku,
       COALESCE(TRY_CAST(units_sold  AS DOUBLE), 0) AS units_sold,
       TRY_CAST(unit_price_ngn AS DOUBLE)           AS unit_price_ngn,
       CAST(on_promotion  AS INTEGER)               AS on_promotion,
       CAST(discount_pct  AS DOUBLE)                AS discount_pct,
       CAST(stockout_flag AS INTEGER)               AS stockout_flag,
       COALESCE(TRY_CAST(revenue_ngn AS DOUBLE), 0) AS revenue_ngn,
       units_sold IS NULL                           AS units_was_blank
FROM bronze.fmcg_sell_out
QUALIFY row_number() OVER (PARTITION BY week_starting, depot_code, sku ORDER BY _row) = 1;
practice/sql/silver/04_regional_report.sql
-- silver.regional_report: Finance's printed FY2025 Excel report made tidy, for reconciliation.
-- Fill the merged region cells down, drop the "All depots" total and the footnote, unpivot the
-- twelve month columns, and turn "₦149,023,348" into a number.
CREATE OR REPLACE TABLE silver.regional_report AS
WITH filled AS (
  SELECT last_value(region IGNORE NULLS) OVER (ORDER BY _row) AS region, depot,
         Jan, Feb, Mar, Apr, May, Jun, Jul, Aug, Sep, Oct, Nov, Dec
  FROM bronze.regional_report
  WHERE depot IS NOT NULL AND depot <> 'All depots'
), long AS (
  UNPIVOT filled ON Jan, Feb, Mar, Apr, May, Jun, Jul, Aug, Sep, Oct, Nov, Dec INTO NAME mon VALUE revenue_txt
)
SELECT region, depot AS depot_name,
       strptime('2025 ' || mon || ' 01', '%Y %b %d')::DATE            AS month,
       CAST(regexp_replace(revenue_txt, '[^0-9.]', '', 'g') AS DOUBLE) AS revenue_ngn
FROM long;

The other three (01_depots.sql, 02_products.sql, 05_marketing_and_macro.sql) are in practice/sql/silver/ in the kit.

💾 Commit: "Silver layer".

F.9 Stage 6 · Gold: model for decisions

🎯 Goal: facts and dimensions at a declared grain, small marts for spreadsheet users, and one wide view for the dashboard.

First decide the shape; then write it.

🧠 Prompt F6a — design the gold layer

[[Session primer, then attach ai_context.md and brief.md.]] Propose a gold layer for the decisions in my brief. For each fact table, write its grain in one sentence (“one row per … per …”). List the dimensions and which facts use them (a bus matrix). Propose marts for people who will use Excel or Power BI. Finally, define one wide view, gold.v_dashboard, that the dashboard will read: exactly one date column, the breakdown columns from my brief (as text), and the measure columns needed for my key numbers. Warn me about any join that could multiply rows (fan-out). Don’t write SQL yet.

🧠 Prompt F6b — write the gold SQL

Good. Now write the files sql/gold/01_dimensions.sql, 02_[[fact]].sql, 03_v_dashboard.sql and 04_marts.sql for that design, reading only silver tables. Use CREATE OR REPLACE TABLE for facts, dimensions and marts and CREATE OR REPLACE VIEW for gold.v_dashboard. Put the grain sentence as a comment at the top of each fact. Then give me a query that proves gold.v_dashboard has exactly as many rows as the fact table.

Rscript run_pipeline.R --to=gold

✔ Check. gold.v_dashboard has the same row count as its fact table (no fan-out). Its date column really is a date. Its breakdown columns hold the values people use in meetings (names, not codes).

📗 Reference answer (practice organisation) 
practice/sql/gold/02_fct_sales.sql
-- Grain: one row per week x depot x SKU (a periodic snapshot fact).
CREATE OR REPLACE TABLE gold.fct_sales AS
SELECT s.week_starting, s.depot_code, s.sku,
       s.units_sold, s.revenue_ngn,
       s.revenue_ngn - s.units_sold * p.unit_cost_ngn AS gross_profit_ngn,
       s.on_promotion, s.discount_pct, s.stockout_flag, s.units_was_blank
FROM silver.sell_out s
JOIN silver.products p USING (sku);
practice/sql/gold/03_v_dashboard.sql
-- The one wide view the dashboard and the semantic layer read: the star, pre-joined.
CREATE OR REPLACE VIEW gold.v_dashboard AS
SELECT f.week_starting, d.region, d.depot_name, p.category, p.product_name,
       f.units_sold, f.revenue_ngn, f.gross_profit_ngn, f.on_promotion, f.discount_pct, f.stockout_flag
FROM gold.fct_sales f
JOIN gold.dim_depot   d USING (depot_code)
JOIN gold.dim_product p USING (sku);

The dimensions and marts are in practice/sql/gold/ in the kit.

💾 Commit: "Gold layer".

F.10 Stage 7 · The publish gate

🎯 Goal: automated tests that stop wrong numbers from ever reaching the dashboard.

Each test in tests/tests.yml counts the rows that break a rule. Zero means PASS. With severity: error (the default), any failure keeps the previous good warehouse live; severity: warn reports but still publishes. The eight types are the ones in Chapter 9: unique, not_null, accepted, range, relationship, fresh, rowcount and custom (any SQL that returns a count).

🧠 Prompt F7 — write the gate

[[Session primer, then attach ai_context.md and brief.md.]] Write tests/tests.yml for my gold layer, using the kit’s test types (unique, not_null, accepted, range, relationship, fresh, rowcount, custom). I need: uniqueness at every fact’s grain and of every dimension key; not-null key measures; plausible ranges ([[e.g. discount 0–50%, quantities ≥ 0]]); accepted codes for [[columns]]; every fact key present in its dimension; a minimum row count; freshness of [[N]] days as a warning; and a custom reconciliation: [[measure]] for [[period]] must match [[authoritative report]] within [[1%]] per [[unit]]. For each test, add a comment saying which failure it catches.

Rscript run_pipeline.R --to=test

✔ Check.

  • Every test runs and says PASS (or WARN for freshness on old data).
  • Prove the gate works. Copy a raw file, break one value on purpose (a negative quantity, a duplicated line), run the full pipeline, and watch it refuse to publish: FAIL, an ALERT line, and warehouse.failed.duckdb kept for inspection. Restore the file and run again.
  • If the reconciliation fails on real data, don’t loosen it. Find out why. It is the most valuable test you have.
📗 Reference answer (practice organisation) 
practice/tests/tests.yml
# Practice organisation: the publish gate (reference answer for Stage 7)
- {type: unique,       table: gold.fct_sales,   columns: [week_starting, depot_code, sku]}
- {type: unique,       table: gold.dim_depot,   columns: [depot_code]}
- {type: unique,       table: gold.dim_product, columns: [sku]}
- {type: not_null,     table: gold.fct_sales,   column: revenue_ngn}
- {type: range,        table: gold.fct_sales,   column: units_sold,   min: 0}

F.12 Stage 9 · One command: run the whole pipeline

🎯 Goal: raw data to a tested, published warehouse with one command, safe to run at any time.

Rscript run_pipeline.R

What happens, in order:

  1. A fresh copy of the warehouse is built from the raw data: bronze, silver, gold.
  2. The tests run. Results are stored in the warehouse and appended to logs/test_history.csv.
  3. Gate open: the new warehouse replaces the live one in a single rename (the atomic swap), and every gold table is copied to data/serve/mart.sqlite for Excel and Power BI users.
  4. Gate closed: nothing changes for users. The failed build is kept as warehouse.failed.duckdb, and an alert goes to logs/alerts.log (and to Teams or Slack, if you set ALERT_WEBHOOK_URL).
  5. A lock file stops two runs overlapping, and logs/run_history.csv records every run.

F.17 Stage 14 · Extensions (optional)
