14.2 A production-grade runner in 40 lines

🧠 Prompt 14.1 — a robust pipeline runner

Write run_platform() for my retail pipeline. It should: build into a temporary DuckDB file so the live warehouse is never half-built; time each step and log it; retry the ingest step up to 3 times with a back-off; run the tests; swap the new warehouse in only if the gate passes; otherwise keep the old file and raise an alert; and return a one-line status summary. Make it safe to run twice at the same time with a lock file.

run_platform <- function(live = "_platform/retail_live.duckdb", as_of = as.Date("2026-04-14"), alert = message) {
  lock <- paste0(live, ".lock")
  if (file.exists(lock)) stop("Another run is in progress (", lock, ")")
  file.create(lock); on.exit(unlink(lock), add = TRUE)
  tmp <- paste0(live, ".building"); unlink(c(tmp, paste0(tmp, ".wal")))
  con <- platform_connect(tmp); t0 <- Sys.time()
  step <- function(name, expr, retries = 0) {
    for (i in 0:retries) {
      s <- Sys.time()
      ok <- tryCatch({ force(expr); TRUE }, error = function(e) { alert(sprintf("[%s] attempt %d failed: %s", name, i + 1, conditionMessage(e))); FALSE })
      if (ok) { log_event(con, "step", name, round(as.numeric(difftime(Sys.time(), s, units = "secs")), 2), "seconds"); return(invisible(TRUE)) }
      Sys.sleep(2^i / 10)                                  # back-off before retrying
    }
    stop("Step failed after retries: ", name)
  }
  step("ingest", retail_bronze(con), retries = 2)
  step("silver", retail_run(con, "silver"))
  step("gold",   retail_run(con, "gold"))
  res <- run_tests(con, retail_tests(as_of = as_of))
  passed <- gate(res)
  dbDisconnect(con, shutdown = TRUE)
  if (passed) { unlink(live); file.rename(tmp, live) } else { alert("GATE CLOSED: live warehouse unchanged"); unlink(tmp) }
  sprintf("%s | %s | %d/%d tests passed | %.1fs", format(Sys.time(), "%Y-%m-%d %H:%M"),
          if (passed) "PUBLISHED" else "BLOCKED", sum(res$status == "PASS"), nrow(res),
          as.numeric(difftime(Sys.time(), t0, units = "secs")))
}

Five properties of a production pipeline
  1. Atomic: consumers see the old version or the new one, never half of each (build to a temp file, then swap).
  2. Idempotent: re-running after a failure is always safe (Chapter 6).
  3. Observable: every step logs what it did and how long it took.
  4. Guarded: tests decide whether to publish, and humans don’t (Chapter 9).
  5. Exclusive: a lock stops two runs colliding.

14.3 Scheduling

Where it runs Scheduler Good for
A laptop or office personal computer (PC) macOS launchd, Linux cron, Windows Task Scheduler Pilots. It breaks when the laptop sleeps
A small virtual machine (VM) or server cron + Rscript refresh.R Small teams; cheapest always-on option
GitHub GitHub Actions schedule: Free for modest workloads; logs and history built in
Posit Connect Scheduled Quarto documents Organisations already using Posit
Cloud orchestrators Azure Data Factory, Airflow, Dagster, Prefect Many pipelines with dependencies between them

A cron line, for 05:30 Lagos time every day:

30 5 * * *  cd /srv/platform && /usr/bin/Rscript refresh.R >> logs/cron.log 2>&1

For larger graphs, R’s targets package works out which steps are out of date and reruns only those, like a make-file for data:

# _targets.R
library(targets)
tar_option_set(packages = c("DBI", "duckdb"))
list(
  tar_target(sellout_file, raw_path("fmcg_sell_out.csv"), format = "file"),   # re-runs only if the file changes
  tar_target(bronze, { con <- platform_connect(); retail_bronze(con); TRUE }),
  tar_target(silver, { bronze; con <- platform_connect(); retail_run(con, "silver"); TRUE }),
  tar_target(gold,   { silver; con <- platform_connect(); retail_run(con, "gold"); TRUE }),
  tar_target(tests,  { gold; run_tests(platform_connect(), retail_tests()) }),
  tar_target(publish, if (gate(tests)) publish_sqlite(platform_connect(), "gold.fct_sales", "mart.sqlite"))
)

14.4 Monitoring and alerting

What to watch, and the threshold that should wake someone up:

Signal Source Alert when
Run status run_platform() return value any BLOCKED or failed step
Freshness t_fresh() latest data older than the service-level agreement (SLA)
Duration ops.run_log step timings > 2× the 30-day median, an early sign of growth or a bad query
Test failure trend ops.test_log the same warning three runs in a row
Volume t_rowcount(), rows per load today’s load < 50% of the trailing average
Dashboard usage server logs a key dashboard unused for 30 days (Chapter 13)

Alerts go where people already are: email, Microsoft Teams or Slack webhooks, or Short Message Service (SMS) for critical regulatory feeds. Every alert names an owner and links to a runbook.

14.5 The runbook

🧠 Prompt 14.2 — write the runbook

Write a one-page runbook for the nightly retail platform refresh: what it does, schedule and SLA, how to tell it failed, the five most likely failures with diagnosis and fix steps (source file late, schema drift, test failure, disk full, lock left behind), how to re-run safely, how to backfill a past week, and who to escalate to.

A runbook entry looks like this:

Failure: GATE CLOSED — unique(gold.fct_sales) failing. Likely cause: the source re-sent a week, or a delivery was double-dropped. Diagnose: SELECT _source_file, COUNT(*) FROM bronze.fmcg_sell_out GROUP BY 1 to see which file appeared twice. Fix: remove the duplicate delivery from the drop folder; re-run Rscript refresh.R. The manifest makes this safe. Escalate: if the source insists both files are valid, raise to the Commercial Finance steward. The rule “first load wins” may need to change.

14.6 Backfills and reprocessing

Because bronze keeps everything and silver and gold are pure functions of bronze, reprocessing history is just a re-run. When a cleaning rule changes (say, a new duplicate rule), you:

  1. change the rule in code, in a pull request;
  2. rebuild silver and gold from bronze;
  3. compare old and new gold (the reconciliation test, against yesterday’s mart);
  4. publish, and note the restatement in the change log.

This is the payoff of never editing bronze.

E14.1. The second run stops immediately with “Another run is in progress”, because the lock file exists. If a crash leaves a stale lock, the runbook says to check that no R process is running, then delete the .lock file.

teams_alert <- function(msg) {
  url <- Sys.getenv("TEAMS_WEBHOOK")
  if (!nzchar(url)) return(message("ALERT (no webhook set): ", msg))
  httr2::request(url) |> httr2::req_body_json(list(text = msg)) |> httr2::req_perform()
}
teams_alert("Test alert from the TDBG platform")

duration_watch <- function(log) {
  log |> dplyr::group_by(object) |>
    dplyr::summarise(median_s = median(rows), latest_s = dplyr::last(rows), .groups = "drop") |>
    dplyr::mutate(flag = latest_s > 2 * median_s)
}
set.seed(1)
sim <- data.frame(object = rep(c("ingest", "silver", "gold"), 10), rows = c(replicate(10, c(1.2, .5, .4)) + runif(30, 0, .1)))
sim$rows[30] <- 1.5                                     # the last gold run was slow
duration_watch(sim)

14.9 🏢 In the organisation

Publish the platform’s SLA and its monthly record (“refresh met SLA on 29 of 30 days; one failure caught by the gate, no wrong data published”). It is the most persuasive slide you can show an executive committee, because it reframes analytics from “the reports team” to “a service we can rely on”.
