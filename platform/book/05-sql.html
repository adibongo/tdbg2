5  SQL: the language of the warehouse

🔵 Practitioner

What The ~20 SQL ideas that cover 95% of analytics work, practised in DuckDB
Why Every layer from silver onward is written in SQL. It is the one language every database, BI tool and AI assistant shares
When From now on, whenever you transform or question data in the warehouse
Who Analysts write it. Reviewers read it. AI drafts it, and you must be able to check it

This chapter uses a pre-built copy of the running example. Chapters 6–8 show how it was built. Every block below is a SQL chunk: Quarto runs it directly against DuckDB.

GROUP BY ALL (DuckDB, Snowflake and BigQuery) groups by every non-aggregated column, which saves typing and prevents mistakes. Use HAVING to filter after aggregating:

GROUP BY ALL
HAVING SUM(units_sold) > 400000

5.3 Combining: JOINs

A join answers “for each row here, find the matching row(s) there.” Four types matter:

Join Keeps Business use
INNER JOIN only matches facts that have a valid dimension
LEFT JOIN all left rows, matched or not “all depots, with sales if any”
ANTI JOIN / NOT EXISTS left rows with no match orphans and data-quality checks
FULL JOIN everything from both sides reconciliation between two sources 
-- Reconcile the Excel regional report to the warehouse, depot by depot (FULL JOIN shows gaps on both sides)
WITH xl AS (SELECT depot_name, SUM(revenue_ngn) AS excel_ngn FROM silver.regional_report GROUP BY 1),
     wh AS (SELECT d.depot_name, SUM(f.revenue_ngn) AS warehouse_ngn
            FROM gold.fct_sales f JOIN silver.depot_history d
              ON f.depot_code = d.depot_code AND d.version = 1
            WHERE year(f.week_starting) = 2025 GROUP BY 1)
SELECT COALESCE(xl.depot_name, wh.depot_name) AS depot,
       round(excel_ngn / 1e6, 1)     AS excel_m,
       round(warehouse_ngn / 1e6, 1) AS warehouse_m,
       round(100 * (excel_ngn / warehouse_ngn - 1), 2) AS gap_pct
FROM xl FULL JOIN wh ON xl.depot_name = wh.depot_name
ORDER BY abs(gap_pct) DESC NULLS FIRST

The fan-out trap

If the right-hand table has duplicate keys, a join multiplies rows. The duplicated DP04 in the raw depot file would double every Abuja sale. Before trusting a join, check the key is unique on the “one” side (Chapter 9 automates this).

5.4 Building in steps: CTEs (WITH)

Common table expressions name each step. They make long queries readable and reviewable, which matters when AI wrote the first draft:

WITH monthly AS (
  SELECT year_month, region, SUM(revenue_ngn) AS revenue
  FROM gold.v_sales GROUP BY ALL
),
ranked AS (
  SELECT *, rank() OVER (PARTITION BY year_month ORDER BY revenue DESC) AS rnk
  FROM monthly
)
SELECT year_month, region, round(revenue / 1e9, 2) AS revenue_bn
FROM ranked WHERE rnk = 1 AND year_month >= '2025-07'
ORDER BY year_month

5.5 Window functions: the analyst’s superpower

A window function calculates across related rows without collapsing them. You need them for running totals, period-on-period growth, ranks, moving averages and de-duplication.

WITH m AS (SELECT year_month, SUM(revenue_ngn) AS revenue FROM gold.v_sales GROUP BY 1)
SELECT year_month,
       round(revenue / 1e9, 2)                                                   AS revenue_bn,
       round(100 * (revenue / lag(revenue, 12) OVER (ORDER BY year_month) - 1), 1) AS yoy_growth_pct,
       round(AVG(revenue) OVER (ORDER BY year_month ROWS 2 PRECEDING) / 1e9, 2)   AS moving_avg_3m_bn,
       round(SUM(revenue) OVER (PARTITION BY left(year_month, 4) ORDER BY year_month) / 1e9, 2) AS ytd_bn
FROM m ORDER BY year_month DESC LIMIT 8

5.7 R and SQL together

You don’t have to choose. Write SQL in SQL chunks, then pick results up in R with output.var, or use dplyr on a lazy table and let it write the SQL:

q <- tbl(con, I("gold.v_sales")) |>
  filter(year == 2025) |>
  group_by(category) |>
  summarise(revenue_bn = sum(revenue_ngn) / 1e9, margin = sum(gross_profit_ngn) / sum(revenue_ngn)) |>
  arrange(desc(revenue_bn))
show_query(q)
<SQL>
SELECT
  category,
  SUM(revenue_ngn) / 1000000000.0 AS revenue_bn,
  SUM(gross_profit_ngn) / SUM(revenue_ngn) AS margin
FROM (FROM gold.v_sales) AS q01
WHERE ("year" = 2025.0)
GROUP BY category
ORDER BY revenue_bn DESC

🧠 Prompt 5.1 — have AI write SQL, then check it

Using DuckDB SQL on table gold.v_sales (columns: week_starting, depot_code, sku, units_sold, revenue_ngn, gross_profit_ngn, on_promotion, discount_pct, stockout_flag, depot_name, region, state, product_name, category, pack_size, year, quarter, year_month), write a query for “gross margin % by category and region for 2025, ranked within each region”. Use a CTE and a window function. Then list the assumptions you made.

Review checklist for AI-written SQL. Run it every time:

  1. Is the grain right? (one row per what?)
  2. Do the filters match the question? (year, status, test accounts)
  3. Can any join fan out?
  4. Are nulls handled? (SUM ignores them; COUNT(*) doesn’t)
  5. Is any ratio computed as a ratio of sums, not an average of ratios?
  6. Does a sanity total match a known number?

5.9 ✅ Mastery check

  • When do you use HAVING rather than WHERE?
  • What does QUALIFY row_number() OVER (PARTITION BY k ORDER BY t DESC) = 1 do?
  • Why is “average of ratios” usually wrong for margin?

5.10 🏢 In the organisation

Make SQL review part of the culture. No query feeds a board number without a second pair of eyes, and AI-written SQL gets the same review as a junior analyst’s. Keep a shared, Git-versioned folder of “certified queries”. Over time it becomes the seed of your semantic layer.
