6  Bronze: land everything, change nothing

🔵 Practitioner

What The first warehouse layer: a faithful, append-only copy of every source, stamped with lineage
Why So you can always answer “what exactly did we receive, and when?”, and rebuild everything downstream without going back to the source
When Every time data arrives, whether a file drop, an application programming interface (API) pull or a database extract
Who Data engineer or analytics engineer. The source owner agrees the delivery contract

6.1 Bronze rules

  1. Faithful. Store what arrived, as text, with no cleaning. If the source says "12O", bronze says "12O".
  2. Traceable. Every row carries _source_file, _source_system and _loaded_at.
  3. Idempotent. Loading the same delivery twice must not create duplicates.
  4. Additive. New deliveries are appended. Old ones are never edited, because they are your audit trail.
  5. Tolerant. A new column in the source (schema drift) is recorded and flagged. It should not crash the pipeline.

6.2 Your first bronze table

🧠 Prompt 6.1 — bronze ingestion with lineage

Create a DuckDB warehouse with schemas bronze, silver, gold and ops. Write a function that loads a comma-separated values (CSV) into bronze. with every column as VARCHAR, and adds _source_file, _source_system and _loaded_at. Log each load (layer, table, row count) into ops.run_log. Load fmcg_sell_out.csv and show the lineage columns.

bronze_ingest() in R/kit.R is the reviewed answer:

bronze_ingest
function (con, file, table = NULL, system = "files", reader = NULL) 
{
    path <- raw_path(file)
    table <- table %||% gsub("[^a-z0-9]+", "_", tolower(tools::file_path_sans_ext(basename(file))))
    ext <- tolower(tools::file_ext(file))
    reader <- reader %||% switch(ext, csv = sprintf("read_csv_auto(%s, all_varchar = true)", 
        sq(path)), parquet = sprintf("read_parquet(%s)", sq(path)), 
        json = sprintf("read_json_auto(%s)", sq(path)))
    dbExecute(con, sprintf("CREATE OR REPLACE TABLE bronze.%s AS\n     SELECT *, %s AS _source_file, %s AS _source_system, current_timestamp AS _loaded_at\n     FROM %s", 
        table, sq(basename(file)), sq(system), reader))
    n <- dbGetQuery(con, sprintf("SELECT COUNT(*) n FROM bronze.%s", 
        table))$n
    log_event(con, "bronze", table, n, basename(file))
    invisible(n)
}

6.3 Incremental, idempotent loading

Real sources arrive in instalments: a file every week, an extract every night. Reloading everything every time is wasteful, and appending blindly creates duplicates. The pattern is a load manifest: remember the fingerprint (Message-Digest Algorithm 5 (MD5) hash) of every file you have loaded, and skip the ones you’ve seen.

🧠 Prompt 6.2 — incremental loads with a manifest

Write ingest_increment(con, path, table) that (1) computes the file’s MD5, (2) skips it if ops.load_manifest already has that hash, (3) otherwise creates the bronze table on first load or appends with INSERT … BY NAME so new or re-ordered columns don’t break it, and (4) records the hash, file, rows and time in the manifest. Demonstrate with two deliveries of sell-out data, re-running the first to prove idempotency, and make the second delivery contain an extra column.

ingest_increment <- function(con, path, table) {
  dbExecute(con, "CREATE TABLE IF NOT EXISTS ops.load_manifest (md5 VARCHAR, file VARCHAR, tbl VARCHAR, rows BIGINT, loaded_at TIMESTAMP)")
  md5 <- unname(tools::md5sum(path))
  if (nrow(dbGetQuery(con, "SELECT 1 FROM ops.load_manifest WHERE md5 = ?", params = list(md5)))) {
    message("SKIP (already loaded): ", basename(path)); return(invisible(0))
  }
  src <- sprintf("SELECT *, %s AS _source_file, current_timestamp AS _loaded_at
                  FROM read_csv_auto(%s, all_varchar = true)", sq(basename(path)), sq(path))
  if (!has_table(con, "bronze", table)) {
    dbExecute(con, sprintf("CREATE TABLE bronze.%s AS %s", table, src))
  } else {
    new_cols <- setdiff(names(dbGetQuery(con, paste(src, "LIMIT 0"))), names(dbGetQuery(con, sprintf("SELECT * FROM bronze.%s LIMIT 0", table))))
    for (c in new_cols) {                                      # schema drift: add the column, flag it
      dbExecute(con, sprintf('ALTER TABLE bronze.%s ADD COLUMN "%s" VARCHAR', table, c))
      message("SCHEMA DRIFT: new column '", c, "' in ", basename(path))
    }
    dbExecute(con, sprintf("INSERT INTO bronze.%s BY NAME %s", table, src))
  }
  n <- dbGetQuery(con, sprintf("SELECT COUNT(*) n FROM bronze.%s WHERE _source_file = %s", table, sq(basename(path))))$n
  dbExecute(con, "INSERT INTO ops.load_manifest VALUES (?, ?, ?, ?, current_timestamp)", params = list(md5, basename(path), table, n))
  invisible(n)
}

# Simulate two weekly deliveries; the second has a new 'channel' column

The third load was skipped, so the pipeline is idempotent: you can re-run it safely after a failure. The new channel column was added and flagged, not silently dropped, and older rows simply have it empty.

Three load strategies
Strategy How When
Full refresh Drop and reload everything Small sources (< ~1M rows), master data, anything that gets corrected retroactively
Incremental append Load only new files or periods (manifest or watermark) Large event or transaction feeds that never change once written
Incremental merge (upsert) Load changes and MERGE/INSERT OR REPLACE by key Sources that update past records (status changes, late payments)

6.4.1 Official statistics: World Bank, IMF, UNCTAD, UN Comtrade

Almost every business case in Nigeria needs a macro frame: inflation for real growth, the exchange rate for import costs, peer-country growth for market sizing, trade partners for supply risk. The official providers publish this through free APIs. Treat them exactly like internal sources: pull, cache, land with lineage, test. The Lab’s R/open_data.R gives every provider the same tidy shape (source, dataset, indicator, iso3, country, year, value).

🧠 Prompt 6.3 — official statistics into bronze

Using R/open_data.R, pull World Bank World Development Indicators (WDI) indicators (gross domestic product (GDP) growth, inflation, GDP per capita, unemployment, remittances as % of GDP) and International Monetary Fund (IMF) World Economic Outlook series (real GDP growth, inflation, government debt) for Nigeria, Ghana, Kenya, South Africa, Egypt and Côte d’Ivoire, plus Nigeria’s 2023 exports by partner from United Nations (UN) Comtrade. Three lessons hide in that table:

  1. Two official sources rarely agree to the decimal. They differ in base years, revision dates and methods (Nigeria rebased its consumer price index (CPI) in 2025). Store both, and always label the source.
  2. The IMF publishes projections alongside actuals. A chart that splices them together without marking the boundary is misleading. Keep a is_projection flag in silver, and make the semantic layer refuse to sum or average across it.
  3. APIs change and go down. with_cache() falls back to the last good pull, and the freshness test (Chapter 9) tells you when that cache is getting old.

6.7 🏢 In the organisation

Agree a delivery contract with every source owner, covering file name pattern, schedule, format, columns and who to call. Store bronze for at least as long as your audit and retention policy requires. The Nigeria Data Protection Act (NDPA) requires that personal data is not kept longer than necessary, so bronze tables holding personal data need a documented retention period and a purge job (Chapter 15).
